# Чек-лист crewflow

Шаги процесса по порядку: перед созданием задачи, перед запуском, во время, при проблемах, перед
ревью, перед одобрением, перед слиянием, после слияния, еженедельно. Пункт — это что проверить,
а правило — по ссылке: второй формулировки у пункта нет, правило живёт в одном месте —
[docs/MODEL.md](docs/MODEL.md), [PROJECT_RULES.md](PROJECT_RULES.md),
[docs/DESIGN.md](docs/DESIGN.md), журнал практики
[#37](https://github.com/naghuale/crewflow/issues/37) и критерии журнала задачи
[#18](https://github.com/naghuale/crewflow/issues/18). Пункта, за которым нет правила, здесь нет:
он пишется кандидатом в [#37](https://github.com/naghuale/crewflow/issues/37).

**⚪ Описано, не работает — #N** — механизм, который DESIGN описывает, а кода нет. Такой пункт
оставлен, чтобы шаг не потерялся, но сегодня его выполнить нечем; `#N` — задача, которая его
сделает. Пункт без такой пометки — то, что работает в коде `main`. Название состояния в пункте —
то, что crewflow печатает сегодня: `blocked`, `stalled`, `pr-opened` и остальные исходы прогона
(`internal/run/outcome.go`).

**Перед любой новой работой** — какой наблюдаемый факт показывает, что это нужно делать сейчас?
Нет факта (`F-NNN` в [#37](https://github.com/naghuale/crewflow/issues/37)) и не закрывает пункт
текущей вехи — `later`:
[PROJECT_RULES, правило 5](PROJECT_RULES.md#5-одна-текущая-цель),
[правило 2](PROJECT_RULES.md#2-нет-задачи-без-критериев-приёмки).

## Перед созданием задачи

- [ ] Одно изменение и один критерий успеха — [правило 1](PROJECT_RULES.md#1-одна-задача--один-результат)
- [ ] Есть ответ, какой отказ задача предотвращает; нет ответа — `later` — [правило 2](PROJECT_RULES.md#2-нет-задачи-без-критериев-приёмки)
- [ ] Наблюдаемый факт `F-NNN` или пункт текущей вехи; нет ни того, ни другого — `later` — [правило 5](PROJECT_RULES.md#5-одна-текущая-цель)
- [ ] Разделы ТЗ и техническая часть заполнены по [шаблону задачи](.github/ISSUE_TEMPLATE/task.md) — [§7f](docs/DESIGN.md#7f-задача-как-тз)

- [ ] У задачи с меткой `risky` названа категория R1–R6 одной строкой `категория: R2` в «Рисках и решениях»: что именно решает человек — [«Решение человека»](docs/MODEL.md#решение-человека), [правило 8](PROJECT_RULES.md#8-человека-зовут-только-тогда-когда-решение-нельзя-получить-из-фактов), [§7f](docs/DESIGN.md#7f-задача-как-тз)

## При проблемах

- [ ] Исход прогона назван, а не «почти получилось» — [§7](docs/DESIGN.md#7-цикл-задачи)
- [ ] `blocked-secret` не продолжается ничем: это то, что человек должен увидеть — [§7a.1](docs/DESIGN.md#7a1-самовосстановление-по-известной-привычке)
- [ ] Правка после третьей неудачной проверки — только с новым фактом: диагностика, запись в журнал, воспроизводящий тест — [правило 4](PROJECT_RULES.md#4-каждый-ушедший-дефект-превращается-в-контроль)
- [ ] Наблюдение владельца, диагностика и сценарий воспроизведения записаны как факт, с источником и строкой «проверено» — [правило 4](PROJECT_RULES.md#4-каждый-ушедший-дефект-превращается-в-контроль), [#37, «Факт F-NNN»](https://github.com/naghuale/crewflow/issues/37)
- [ ] Простой виден: последний шаг — в `task watch`, исход и причина — в `task list` — [правило 6](PROJECT_RULES.md#6-любое-состояние-требующее-внимания-видно), [§6](docs/DESIGN.md#6-команды)
- [ ] ⚪ Описано, не работает — #108: сломан механизм crewflow — путь восстановления взят из раздела, а не придуман в момент сбоя: обходится только сломанное, gate и `verify` остаются включены, исправление подтверждает независимый механизм, и после пути система вернулась на обычный путь. Триггер — ошибка, факт `F-NNN`, невыполнимый инвариант или провал проверки; слова «посмотрел, должно работать» доказательством не считаются — [правило 6](PROJECT_RULES.md#6-любое-состояние-требующее-внимания-видно), [§7l](docs/DESIGN.md#7l-самовосстановление-self-recovery), [§7h](docs/DESIGN.md#7h-merge-gate--отказ-которому-можно-доверять)
- [ ] ⚪ Описано, не работает — #45, #18, #29: остановка прогона с причиной, события `TASK_STOPPED` и `TASK_RESUMED` со ссылкой на факт, проверка `lesson-unclosed` в `task check` — [правило 4](PROJECT_RULES.md#4-каждый-ушедший-дефект-превращается-в-контроль)
- [ ] ⚪ Описано, не работает — #67: сколько стоим — пометки `stalled` со временем простоя нет — [правило 6](PROJECT_RULES.md#6-любое-состояние-требующее-внимания-видно)

## Перед ревью

- [ ] Изменённые файлы — в границах задачи — [§7c](docs/DESIGN.md#7c-параллельные-задачи)
- [ ] Ворота проекта прошли на коммите, CI на нём зелёное — [§6](docs/DESIGN.md#6-команды), [§7h](docs/DESIGN.md#проверки-перед-слиянием)
- [ ] Доказательство есть: тест, лог, скриншот, шаги; для живой цепочки — тест через настоящую проводку, а не по одному компоненту — [правило 3](PROJECT_RULES.md#3-нет-одобрения-без-доказательства), [§10](docs/DESIGN.md#10-уроки)
- [ ] Данные и фикстуры внешнего источника — в том виде, как их отдаёт источник — [§10](docs/DESIGN.md#10-уроки)

- [ ] Дефект, ушедший в основную ветку, оставил тест, проверку или пункт приёмки — [правило 4](PROJECT_RULES.md#4-каждый-ушедший-дефект-превращается-в-контроль)

## Перед одобрением

- [ ] Перед одобрением — `crewflow review <PR>` и разбор изменений оркестратором, а не «посмотрел и ок» — [§6](docs/DESIGN.md#6-команды), [§4](docs/DESIGN.md#4-понятия)
- [ ] Запись одобрения — на текущей голове, `REVIEW: APPROVED <полный sha>`; после нового коммита — новое ревью — [§7h](docs/DESIGN.md#запись-ревью-и-кто-может-одобрить)
- [ ] Автор записи — из `[merge] reviewers`, и запись не редактировалась после публикации — [§7h](docs/DESIGN.md#запись-ревью-и-кто-может-одобрить)
- [ ] Запись опознаётся по типу и устойчивому номеру, а не по строке логина: человек — по номеру учётной записи, App — по номеру App; переименование не меняет полномочий, а незнакомый вид — отказ, а не права по умолчанию — [IV-021, IV-022](docs/MODEL.md#позиции-практики), [«Кто такой субъект записи»](docs/DESIGN.md#кто-такой-субъект-записи), [правило 9](PROJECT_RULES.md#9-эскалация-идёт-по-фактам-а-не-по-нетерпению)
- [ ] Последняя учитываемая запись — `APPROVED`: `CHANGES REQUESTED` после неё отменяет одобрение — [§7h](docs/DESIGN.md#запись-ревью-и-кто-может-одобрить)
- [ ] Нерешённых замечаний нет — [§7h](docs/DESIGN.md#запись-ревью-и-кто-может-одобрить)
- [ ] Обязательные проверки зелёные и относятся ровно к этому SHA — [§7h](docs/DESIGN.md#проверки-перед-слиянием)
