# Чек-лист crewflow

Шаги процесса по порядку: перед созданием задачи, перед запуском, во время, при проблемах, перед
ревью, перед одобрением, перед слиянием, после слияния, еженедельно. Пункт — это что проверить,
а правило — по ссылке: второй формулировки у пункта нет, правило живёт в одном месте —
[PROJECT_RULES.md](PROJECT_RULES.md), [docs/DESIGN.md](docs/DESIGN.md), журнал практики
[#37](https://github.com/naghuale/crewflow/issues/37) и критерии журнала задачи
[#18](https://github.com/naghuale/crewflow/issues/18). Пункта, за которым нет правила, здесь нет:
он пишется кандидатом в [#37](https://github.com/naghuale/crewflow/issues/37).

**Перед любой новой работой** — какой наблюдаемый факт показывает, что это нужно делать сейчас?
Нет факта (`F-NNN` в [#37](https://github.com/naghuale/crewflow/issues/37)) и не закрывает пункт
текущей вехи — `later`:
[PROJECT_RULES, правило 5](PROJECT_RULES.md#5-одна-текущая-цель),
[правило 2](PROJECT_RULES.md#2-нет-задачи-без-критериев-приёмки).

## Перед созданием задачи

- [ ] Одно изменение и один критерий успеха — [правило 1](PROJECT_RULES.md#1-одна-задача--один-результат)
- [ ] Есть ответ, какой отказ задача предотвращает; нет ответа — `later` — [правило 2](PROJECT_RULES.md#2-нет-задачи-без-критериев-приёмки)
- [ ] Наблюдаемый факт `F-NNN` или пункт текущей вехи; нет ни того, ни другого — `later` — [правило 5](PROJECT_RULES.md#5-одна-текущая-цель)
- [ ] Разделы ТЗ и техническая часть заполнены по [шаблону задачи](.github/ISSUE_TEMPLATE/task.md) — [§7f](docs/DESIGN.md#7f-задача-как-тз)
- [ ] Нужно одобрение владельца — метки `risky` и `approved`; у задачи интерфейса — макет или скриншот эталона — [§7f](docs/DESIGN.md#7f-задача-как-тз)
- [ ] Приоритет назначен: P3 не обсуждается, пока открыты P0 и P1 — [приоритеты](PROJECT_RULES.md#приоритеты)

## Перед запуском

- [ ] `crewflow task check <N>` проходит: разделы, критерии, тесты, пути, `approved` — [§7f](docs/DESIGN.md#7f-задача-как-тз)
- [ ] Границы — список путей (glob) в задаче: по нему же считается `out-of-scope` — [§7c](docs/DESIGN.md#7c-параллельные-задачи)
- [ ] Исполнитель проверен `crewflow doctor`, запасной — в `[executor] fallback` — [§7b](docs/DESIGN.md#7b-если-агента-или-модели-нет)
- [ ] Инструменты проекта есть и проверены — `[requirements]` — [§7d](docs/DESIGN.md#7d-окружение-и-зависимости)
- [ ] Чтения вне рабочей папки объявлены в `[access]` и только на чтение — [§7d](docs/DESIGN.md#7d-окружение-и-зависимости)
- [ ] Нужные возможности объявлены, у каждой — причина и область; разрешение даёт человек — [§7e](docs/DESIGN.md#7e-доступ-к-секретам-и-внешним-системам)
- [ ] Список доступа собран из проекта и выданных разрешений, руками не дописан — [§7a](docs/DESIGN.md#7a-запуск-исполнителя-без-окна)

## Во время выполнения

- [ ] Прогон виден в `crewflow task list` и в `task watch`; отказ — это исход, а не «почти получилось» — [§7](docs/DESIGN.md#7-цикл-задачи)
- [ ] Каждое событие записано там, где его прочтёт новый агент: журнал прогона, состояние, хостинг — [§7](docs/DESIGN.md#7-цикл-задачи)
- [ ] У задачи ровно одно состояние; у «ждёт», «стоит», «остановлена» — причина, время и следующее действие — [#18 AC-3](https://github.com/naghuale/crewflow/issues/18)
- [ ] Ожидание видно в одном месте, с причиной и готовой командой — [правило 6](PROJECT_RULES.md#6-любое-ожидание-видно)
- [ ] Ничего важного не сделано мимо crewflow — [«Действия мимо crewflow» в #37](https://github.com/naghuale/crewflow/issues/37)
- [ ] Покрытие процесса: у каждого действия процесса есть событие — [#18 AC-7](https://github.com/naghuale/crewflow/issues/18)

## При проблемах

- [ ] Исход прогона назван, а не «почти получилось» — [§7](docs/DESIGN.md#7-цикл-задачи)
- [ ] `blocked-secret` не продолжается ничем: это то, что человек должен увидеть — [§7a.1](docs/DESIGN.md#7a1-самовосстановление-по-известной-привычке)
- [ ] Третья неудачная проверка правки — остановка с причиной; продолжение — только со ссылкой на новый факт `F-NNN` — [правило 4](PROJECT_RULES.md#4-каждый-ушедший-дефект-превращается-в-контроль), [#18 AC-5](https://github.com/naghuale/crewflow/issues/18), [#18 AC-6](https://github.com/naghuale/crewflow/issues/18)
- [ ] Наблюдение владельца, диагностика и сценарий воспроизведения записаны как факт, с источником и строкой «проверено» — [правило 4](PROJECT_RULES.md#4-каждый-ушедший-дефект-превращается-в-контроль), [#37, «Факт F-NNN»](https://github.com/naghuale/crewflow/issues/37)
- [ ] Простой виден: последний шаг, сколько стоим, кого и чего ждём — [правило 6](PROJECT_RULES.md#6-любое-ожидание-видно)

## Перед ревью

- [ ] Изменённые файлы — в границах задачи — [§7c](docs/DESIGN.md#7c-параллельные-задачи)
- [ ] Ворота проекта и CI на коммите зелёные — [§7h](docs/DESIGN.md#проверки-перед-слиянием)
- [ ] Доказательство есть: тест, лог, скриншот, шаги; для живой цепочки — тест через настоящую проводку, а не по одному компоненту — [правило 3](PROJECT_RULES.md#3-нет-одобрения-без-доказательства), [§10](docs/DESIGN.md#10-уроки)
- [ ] Данные и фикстуры внешнего источника — в том виде, как их отдаёт источник — [§10](docs/DESIGN.md#10-уроки)
- [ ] Утверждение о внешней системе проверено её собственной командой; иначе «не проверял» — [§10](docs/DESIGN.md#10-уроки)
- [ ] Дефект, ушедший в основную ветку, оставил тест, проверку или пункт приёмки — [правило 4](PROJECT_RULES.md#4-каждый-ушедший-дефект-превращается-в-контроль)

## Перед одобрением

- [ ] Ревью — ворота, CI и разбор изменений, а не «посмотрел и ок» — [§4](docs/DESIGN.md#4-понятия)
- [ ] Запись одобрения — на текущей голове, `REVIEW: APPROVED <полный sha>`; после нового коммита — новое ревью — [§7h](docs/DESIGN.md#запись-ревью-и-кто-может-одобрить)
- [ ] Автор записи — из `[merge] reviewers`, и запись не редактировалась после публикации — [§7h](docs/DESIGN.md#запись-ревью-и-кто-может-одобрить)
- [ ] Последняя учитываемая запись — `APPROVED`: `CHANGES REQUESTED` после неё отменяет одобрение — [§7h](docs/DESIGN.md#запись-ревью-и-кто-может-одобрить)
- [ ] Нерешённых замечаний нет — [§7h](docs/DESIGN.md#запись-ревью-и-кто-может-одобрить)
- [ ] Обязательные проверки зелёные и относятся ровно к этому SHA — [§7h](docs/DESIGN.md#проверки-перед-слиянием)

## Перед слиянием

- [ ] `crewflow review <PR>` отвечает «можно сливать» — [§7h](docs/DESIGN.md#проверки-перед-слиянием)
- [ ] Одобрен ровно текущий head, новых коммитов после одобрения нет — [§8](docs/DESIGN.md#8-инварианты-безопасности)
- [ ] Границы проверены и сейчас: коммит, добавленный после прогона, тоже может выйти за них — [§7h](docs/DESIGN.md#проверки-перед-слиянием)
- [ ] Ни одного `blocked-secret` по задаче — [§8](docs/DESIGN.md#8-инварианты-безопасности)
- [ ] Приёмка владельцем, если задача её требует: запись `ACCEPTED` — [§7k](docs/DESIGN.md#решения), [#18, OWNER_ACCEPTED](https://github.com/naghuale/crewflow/issues/18)
- [ ] Никто не вливает собственную работу: документ идёт задачей, как код — [правило 3](PROJECT_RULES.md#3-нет-одобрения-без-доказательства), [§7i](docs/DESIGN.md#7i-разделение-полномочий)
- [ ] `crewflow merge` — fast-forward ровно одобренного коммита, без `--force` — [§8](docs/DESIGN.md#8-инварианты-безопасности)

## После слияния

- [ ] `crewflow verify <PR>`: ветка на влитом коммите, задача закрыта, CI на основной ветке зелёный — [§6](docs/DESIGN.md#6-команды)
- [ ] Слияние подтверждено на хостинге (`git ls-remote`), а не по коду выхода git — [§7h](docs/DESIGN.md#проверки-перед-слиянием)
- [ ] Запись в [#37](https://github.com/naghuale/crewflow/issues/37): факты, толкование, решение — после слияния, приёмки или заметного события
- [ ] Строка в [CHANGELOG.md](CHANGELOG.md) («Не выпущено»), если это меняет то, что человек увидит или сможет — [правило 3](PROJECT_RULES.md#3-нет-одобрения-без-доказательства)
- [ ] То, что человек увидит, открыто на реальном GitHub, а не принято по описанию — [§10](docs/DESIGN.md#10-уроки)
