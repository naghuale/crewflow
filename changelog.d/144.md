### Добавлено

- **Сеть как ресурс: именованные профили прокси, `direct` / `proxy`, правка командами.**
  Прокси для программ crewflow (`gh`, `git`, исполнитель, `git` ревью и слияний) настраивался
  только переменными окружения вручную, а адрес прокси на машинах разный (F-119, #37, 02.10:
  поставщик модели был недоступен, владелец проверил локальный прокси и сказал «прокси может быть
  разный — нужно редактировать»). Теперь в файле проекта лежит **имя** маршрута, а не адрес:
  `[network] mode` (`direct` | `proxy`; `fallback` — #145, описан и отказ до записи),
  `active_proxy`, `no_proxy`, `connect_timeout`, `test_valid_for` и профили
  `[network.proxies.<имя>]` с `type` (`http` | `https` | `socks5` — только реально
  поддержанные), `host`, `port`, `credentials`. Всё это в реестре (§5).
  Команды: `crewflow network proxy list | add | edit | use | remove | credentials | test` и
  `crewflow network mode direct | proxy`. `edit` (в том числе активного профиля) синтаксически
  неверную правку не сохраняет, а верную сохраняет целиком — верный, но сейчас недоступный
  профиль можно заготовить заранее, и он сам не активируется; активный профиль не удаляется;
  удаление профиля и удаление учётных данных — разные операции. Каждое изменение пишет
  событие `PROXY_PROFILE_CHANGED` без секретов.
  Порядок выбора маршрута (решение владельца 02.10): цель совпала с `no_proxy` → напрямую;
  иначе `direct` → напрямую; `proxy` → активный профиль; `fallback` → #145. `no_proxy`
  проверяется **до** выбора прокси, работает и в режиме `proxy` и читается по стандартным
  правилам `NO_PROXY` — точное имя, доменный суффикс, адрес, сеть в CIDR, `*`,
  необязательный порт; неоднозначный шаблон (со схемой, путём, учётными данными,
  звёздочкой в середине имени) — отказ, а не догадка.
  Применение — **только в окружении дочерних процессов** (`HTTP_PROXY`, `HTTPS_PROXY`,
  `ALL_PROXY`, `NO_PROXY`): глобальное окружение, глобальная и системная настройка git не
  меняются, в режиме `direct` не добавляется ничего, TLS и проверка хоста не ослабляются.
  Учётные данные профиля — в связке ключей под именем `network-proxy/<имя>`; URL с логином и
  паролем (`http://user:pass@…`) отказ; команды показа (`list`, `credentials status`, `test`,
  `doctor network`) знают только `credentials_configured: true/false` и не читают значение —
  читается оно ровно там, где соединение через профиль действительно делается.
  (задача [#144](https://github.com/naghuale/crewflow/issues/144))

- **`crewflow doctor network` и `network proxy test` — возможности раздельно.** Прямой маршрут
  и активный профиль, а внутри каждого `github-api`, `git-https` и `model-provider` по
  отдельному слову, со временем проверки и её свежестью: `available` / `unavailable` /
  `unknown` / `stale` (старше `test_valid_for`). «Профиль есть» ≠ «профиль работает»,
  непроверенное — `unknown`, успех GitHub не доказывает поставщика модели, а «исполнитель
  использует прокси» остаётся `unknown`, пока это не доказано пробным запросом. Проверка
  доступности **не хранится в настройке**: в `crewflow.toml` только заявленная конфигурация.
  `doctor` (без `network`) по-прежнему не идёт в сеть и говорит одной строкой `network route`,
  куда обращаться за живой проверкой; живая проверка — отдельная команда, потому что отчёт о
  готовности машины не должен ждать чужой прокси.

  Подробности — §7d, «Сеть как ресурс».
  (задача [#144](https://github.com/naghuale/crewflow/issues/144))
