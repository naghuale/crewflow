### Добавлено

- **Режим `fallback`: прямо и одна попытка через прокси при доказанной сетевой
  недоступности.** Когда прямой маршрут недоступен (GitHub, поставщик модели), прогон падал,
  хотя рабочий прокси в проекте уже был настроен; когда недоступно всё — причины не было видно
  (F-119, #37, 02.10). Теперь `[network] mode = "fallback"` — третий режим рядом с `direct` и
  `proxy`, и `crewflow network mode fallback` его записывает (без `active_proxy` режим отказ до
  записи, а не «маршрут без второй попытки»).
  Маршрут выбирает сетевой механизм по настройке и по доступности, а не оркестратор вручную:
  запрос идёт **напрямую**, и только при **доказанной повторяемой** сетевой недоступности —
  ровно **одна** попытка через активный профиль (`fallback_attempts = 1`, политика §7d). Поводом
  служат только пять доказанных причин закрытого списка §7d: `dns-failed`,
  `connection-refused`, `connection-timeout`, `tls-failed`,
  `proxy-authentication-required`. Режим **не** применяется при отказе входа (401), отсутствии
  прав (403), неверном запросе (404), ошибке настройки или задачи и **неизвестной** ошибке:
  сеть дошла, а не дошла учётная запись или право — это решение человека, а не другая дорога.
  **Fallback — на уровне одной операции** (решение владельца 02.10): отказ GitHub API → этот один
  запрос повторён через прокси; следующие вызовы `git`, исполнителя и `doctor` **не** переводятся
  на прокси. Постоянная смена маршрута — только явной командой (`network proxy use`,
  `network mode proxy`).
  **Оба маршрута недоступны** → «ждёт», причина **`network-route-unavailable`**: в очереди —
  прямой недоступен, прокси `<имя>` недоступен (у каждого своя доказанная причина), работа
  сохранена, команда продолжения `crewflow task run <N> -continue "…"`. Crewflow сам не идёт
  дальше: одна вторая попытка обещана и потрачена, третья — решение человека.
  **Смена маршрута не меняет полномочия субъекта** (SEC-NET-009): вторая попытка — тот же
  процесс, тот же аккаунт и тот же токен, что и первая; другой маршрут — не другое право.
  События `NETWORK_ROUTE_SELECTED`, `NETWORK_ROUTE_FAILED`, `NETWORK_FALLBACK_STARTED`,
  `NETWORK_FALLBACK_SUCCEEDED`, `NETWORK_FALLBACK_FAILED` идут в журнал прогона и **без
  секретов**: значение учётных данных читается ради соединения (в том числе профиля второй
  попытки — в момент самой попытки) и никогда не пишется, а слова программы в событии
  проходят через редактор секретов. Подробности — §7d, «Режим `fallback`».
  (задача [#145](https://github.com/naghuale/crewflow/issues/145))
### Исправлено

- **Тесты пакета `internal/network` больше не достают до сети машины, на которой их
  запускают.** Проверка маршрута через профиль набирала адрес **того** прокси, который был
  назван в файле проекта, и фаервол машины владельца спросил, что это за процесс
  (`network.test`, 03.10 ≈08:00). У проверки маршрута теперь есть собственный dialer
  (`Machine.Dial`), а у тестов пакета — общий предохранитель: соединение разрешено только к
  `127.0.0.1` и `::1` (плюс `localhost`), всё остальное — имя или адрес — fail'ится в тесте с
  указанием набранного адреса; `TestMain` пакета убирает из окружения `HTTP_PROXY`, `HTTPS_PROXY`,
  `ALL_PROXY`, `NO_PROXY` и их строчные варианты, чтобы прокси оболочки не достался ни одной
  программе, которую запустил тест. Проверки, которым нужен настоящий прокси, поднимают его на
  `127.0.0.1` внутри теста, как и сервер API.
  Адрес прокси владельца убран из репозитория (README, DESIGN, пример
  `crewflow.toml`, тесты): у документации — адрес `192.0.2.10` (RFC 5737) и `proxy.example.org`,
  а машина владельца не принадлежит публичному репозиторию.
  (задача [#145](https://github.com/naghuale/crewflow/issues/145))
