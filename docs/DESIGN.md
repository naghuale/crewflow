# crewflow — устройство

Статус: **черновик на согласование**.

## 1. Зачем

> crewflow — fail-closed протокол доставки изменений для кодирующих агентов: хостинг git остаётся
> источником правды, одобрение привязано к конкретному SHA, а слияние возможно только через
> проверенные ворота fast-forward.

**Что здесь главное:** merge gate (§7h) и разделение полномочий (§7i). Остальное — настройки,
окружение и удобство вокруг них.

crewflow — небольшой фреймворк для разработки связкой двух ролей:

- **оркестратор** ставит задачи, проверяет результат и решает, что вливать;
- **исполнитель** пишет код и тесты по задаче.

Роли не привязаны ни к конкретному агенту, ни к конкретной модели. Оркестратором может быть
любой агент, который умеет запускать команды (Claude Code, Codex, Gemini CLI, OpenCode…), а
исполнителем — любой агент с режимом без окна. Модель выбирает сам агент по своим настройкам;
crewflow передаёт модель, только если она явно указана в `crewflow.toml`. Готовые описания
исполнителей (адаптеры) — лишь примеры; первым проверен OpenCode.

Цель — чтобы цикл «задача → код → ревью → слияние → проверка» шёл сам, без ручной
передачи сигналов, открытых окон и подталкиваний, а человек участвовал только в решениях.

Фреймворк **не зависит от проекта**: язык, стек, команды сборки и проверок, соглашения —
всё задаётся настройками. Первым проектом, на котором его обкатывают, был telecli (Go + TDLib),
но ни одна его деталь не зашита в ядро.

## 2. Откуда идеи

- **Практика telecli** (27 задач, сентябрь 2026): GitHub issue и PR как источник правды,
  одобрение конкретного коммита комментарием `REVIEW: APPROVED <sha>`, слияние только при
  зелёном CI и только fast-forward, сверка `main` после слияния, «не верить самоотчёту — проверять
  самому».
- **[zeroscrypt/aiac](https://github.com/zeroscrypt/aiac)** (Apache-2.0): оркестратор сам
  запускает исполнителя без окна, отдельный `git worktree` на задачу, Definition of Ready и
  Definition of Done, уроки из живых багов процесса.

Что снимает crewflow по сравнению с тем, как шла работа в telecli: исполнитель в отдельном окне
не видел сообщений, сессии множились и кончался бюджет, общая рабочая папка ломалась при
параллельной работе, каждое ревью собиралось руками.

## 3. Не цели

- Не генератор кода и не агент: crewflow ничего не пишет сам, он управляет циклом.
- Не замена CI: он читает результат CI, а не повторяет его.
- Не многопользовательский сервис: один человек, один оркестратор, локальная машина.
- Не зашивать один язык, один менеджер пакетов, одного агента или одну модель.

## 4. Понятия

| Понятие | Что это |
|---|---|
| Проект | Любой git-репозиторий с файлом `crewflow.toml` в корне — на GitHub, GitLab, Bitbucket или вовсе без хостинга (§7g). |
| Задача | GitHub issue по шаблону crewflow из двух частей: ТЗ для человека и техническая часть для исполнителя (§7f). |
| Ворота (gates) | Команды проекта, которые обязаны пройти на коммите: форматирование, линтер, тесты, сборка. |
| Прогон (run) | Один запуск исполнителя над одной задачей в своём worktree. Результат — PR с `Closes #N`. |
| Запрос на изменение | PR в GitHub, MR в GitLab, PR в Bitbucket — в ядре одно понятие (§7g). Ниже для краткости «PR». |
| Ревью | Прогон ворот на голове PR + CI + проверки оркестратора → комментарий `REVIEW: APPROVED <sha>` или `REVIEW: CHANGES REQUESTED`. |
| Слияние | fast-forward `main` до одобренного коммита, только если одобрен ровно текущий head и CI зелёный. |
| Сверка | `origin/main` == влитый коммит, issue закрыт, CI на `main` зелёный. |

## 5. Настройки: `crewflow.toml`

Один файл в корне проекта. Пример для telecli:

```toml
[project]
repo = "naghuale/tele"
default_branch = "main"
language = "ru"            # язык задач, ревью и сообщений человеку

[forge]                    # хостинг кода и ревью (§7g)
kind = "github"            # github | gitlab | bitbucket | gitea | azure | none
host = ""                  # свой сервер, например "gitlab.company.com"; пусто — публичный

[tracker]                  # где живут задачи (§7g)
kind = "forge"             # forge | jira | linear | files
project = ""               # ключ проекта в трекере, если он не совпадает с репозиторием

[identity]                 # от чьего имени работает исполнитель (§7i)
mode = "owner"             # owner — вход владельца (по умолчанию); bot — отдельная учётная запись хостинга
# В режиме bot подтаблица хостинга: у GitHub это приложение. app_id — номер
# приложения в настройках GitHub, installation_id — номер его установки на
# репозиторий (0 — найдётся сама).
# [identity.github_app]
# app_id = 5107052
# installation_id = 0


[executor]
# Любой агент с режимом без окна. Шаблон команды; {worktree} и {prompt} подставляет crewflow.
command = ["opencode", "run", "--dir", "{worktree}", "--format", "json", "{prompt}"]
model = ""                 # пусто — модель по умолчанию из настроек самого агента
model_flag = ["--model", "{model}"]   # как агент принимает модель; добавляется, только если model задана
timeout = "90m"
fallback = []              # запасные исполнители по порядку (такие же таблицы), если основной недоступен

[access]
# Что исполнитель может читать вне рабочей папки задачи (§7d). Пути на машинах
# разные, поэтому проект говорит, КАК их найти: команда печатает пути, по одному на
# строку. Читать — можно, писать — нельзя.
read_from = [["go", "env", "GOMODCACHE"], ["go", "env", "GOROOT"]]
read = []                  # постоянные пути, которые читать можно всегда; ~ раскрывается

[requirements]
# Что нужно проекту — инструменты и как их проверить. Путей здесь нет: они на разных
# машинах разные и определяются сами (§7d).
tools = [
  { name = "go", check = ["go", "version"], min = "1.27" },
  { name = "golangci-lint", check = ["golangci-lint", "version"] },
  { name = "libtdjson", check = ["sh", "-c", "test -e \"$TELECLI_TDLIB_LIBRARY\""] },
]

[isolation]
mode = "host"              # host | sandbox | container (§7d)

[[capabilities]]
# Доступ к секретам и внешним системам, который проекту может понадобиться (§7e).
# Здесь только объявление; разрешает человек, и хранится разрешение на машине.
name = "github-keys"
use = ["gh"]               # пользоваться через посредника, не видя секрета
actions = ["gh ssh-key add", "gh gpg-key add"]   # действия с последствиями снаружи — всегда с подтверждением

[worktrees]
root = "~/.crewflow/worktrees/{repo}"   # вне рабочей папки человека

[[gates]]
name = "format"
run = ["sh", "-c", "test -z \"$(gofmt -l .)\""]

[[gates]]
name = "vet"
run = ["go", "vet", "./..."]

[[gates]]
name = "test"
run = ["go", "test", "-race", "-count=1", "./..."]

[[gates]]
name = "lint"
run = ["golangci-lint", "run", "./..."]

[ci]
kind = "forge"             # forge | jenkins | command | none (§7g)
required = true            # ждать и требовать зелёный CI на коммите
timeout = "30m"

[merge]
by = "orchestrator"        # orchestrator | executor | human
strategy = "ff-only"
via = "git-push"           # git-push | forge — через API хостинга, если main защищён (§7g)
# Логины, чья запись ревью считается одобрением (§7h). Пусто — владелец репозитория.
# Запись исполнителя одобрением не считается, что бы он ни написал под своим PR.
reviewers = []

[parallel]
max_tasks = 1              # сколько задач могут идти одновременно; 1 — строго по очереди

[tasks]
owner_approval = "risky"   # all | risky | none — какие ТЗ ждут одобрения человека (§7f)
```

Для проекта на другом стеке меняется только `[[gates]]`: `npm test`, `pytest`, `cargo test`,
`make check` — что угодно, что возвращает код выхода.

## 6. Команды

| Команда | Что делает |
|---|---|
| `crewflow init` | Кладёт `crewflow.toml`, шаблоны issue/PR и протокол в проект. Существующие файлы не трогает. |
| `crewflow doctor` | Проверяет, что есть `git`, `gh` (с входом), исполнитель, команды ворот; что `crewflow.toml` читается. |
| `crewflow task run <N>` | Проверяет готовность issue (DoR), создаёт ветку и worktree, запускает исполнителя с текстом issue и протоколом, ждёт завершения, проверяет, что появился PR с `Closes #N`. |
| `crewflow review <PR>` | Собирает факты о PR из хостинга и из git (голова, записи ревью, обязательные проверки, изменённые файлы, история) и говорит одно: можно вливать или нельзя, и если нельзя — то почему, одним словом из §7h. Правила читает код, а не оркестратор. `-approve` и `-request-changes <файл>` пишут запись ревью ровно на текущую голову в формате §7h, и только если `Evaluate` без учёта одобрения даёт готовность; запись пишется от лица владельца (логин `gh`), и crewflow отказывается, если это не один из `[merge] reviewers`. Ворот проекта (`[[gates]]`) в worktree голы эта команда не гоняет: их гоняет исполнитель перед PR и CI на коммите после слияния — это отдельная задача M2. |
| `crewflow merge <PR>` | Сливает только если: есть `REVIEW: APPROVED <sha>` с sha == head, CI на head зелёный, `main` — предок head. Иначе объясняет, чего не хватает. Результат проверяется по `git ls-remote` (удалённый `main` == sha), а не по коду выхода `git push`; полный вывод git сохраняется; остальные шаги (удаление worktree, ветки) — только после подтверждённого слияния. Урок пилота: «первый push падает» оказался не сетью, а оболочкой — в zsh `$SHA:refs/…` читается как модификатор `:r`; команды собираются массивом аргументов, без интерполяции в оболочке. |
| `crewflow verify <PR>` | Сверка после слияния: `origin/main`, закрытый issue, CI на `main`. |
| `crewflow task check <N>` | Только проверка готовности ТЗ и одобрения; ничего не создаёт. |
| `crewflow task watch <N>` | Читаемый журнал последней (или `-attempt K`) попытки; пока прогон идёт — следит за ним. |
| `crewflow task list` | Все задачи проекта, по которым были прогоны: сверху те, что требуют внимания (`running`, `blocked`, `blocked-secret`, `blocked-permission`, `interrupted`, `timeout`, `executor-failed`, `maybe-running`), ниже остальные от последней попытки к более ранней. Над таблицей — проект и сколько у него задач, под ней — что ещё идёт на этой машине и как посмотреть всё. По каждой — исполнитель (ИИ-агент), от чьего имени он работал, исход последней попытки, когда и сколько длилась, номер прогона `<N>-<K>` и номер PR. Читает только `~/.crewflow/state/<repo>/<N>.json`, без сети; без `-all` — последние 20. `-all` — откуда угодно, все проекты, у которых есть прогоны, и все их прогоны, колонка `REPO` первая, без `crewflow.toml`; вместе с `-repo` — ошибка использования. |
| `crewflow status` | Что в работе: открытые задачи, прогоны, PR и их состояние. |
| `crewflow auth app import <файл.pem>` | Кладёт ключ GitHub App в связку ключей macOS; ничего из ключа не печатает, после импорта советует удалить файл (§7i). |
| `crewflow auth app check` | Ключ есть, App установлен на репозиторий, права — и не шире, чем нужно прогону. Токен не печатает (§7i). |

Все команды умеют `--json` для оркестратора и печатают человеку понятный текст на языке проекта.

## 7. Цикл задачи

```
issue (готов по DoR)
  → task run: worktree + ветка → исполнитель → PR (Closes #N)
  → review: ворота + CI + проверки оркестратора
      ├─ changes requested → task run --continue (тот же worktree и ветка) → review
      └─ approved <sha>
  → merge (ff-only, sha == head, CI зелёный)
  → verify (main, issue, CI на main)
```

Итоги прогона: `pr-opened`, `blocked-permission`, `blocked-secret`, `blocked`, `timeout`,
`no-change-request`, `executor-failed`, `out-of-scope`, `interrupted` (crewflow остановлен
сигналом — исполнитель останавливается тоже). `blocked-secret` — отказ, который касается места
из списка запретов (§7d): он не «ещё один отказ», а отдельный исход, который оркестратор читает
первым. Журнал пишется по ходу прогона; стиль коммитов исполнитель берёт из
`git log` проекта или из `[project] commit_style`.

Состояние задачи хранится в `~/.crewflow/state/<repo>/<N>.json` (ветка, worktree, `base_sha`,
попытки: исполнитель, сессия, время, исход, номер процесса прогона crewflow и когда он начался;
ссылка на открытый PR), чтобы после обрыва было видно, где остановились. Там только факты;
одобрение и готовность к слиянию не хранятся, а вычисляются (§7h). Источник правды — хостинг.

`crewflow task list` читает только эти файлы, и ничего больше: ни трекера, ни хостинга, ни
сети. Название задачи в них — текст с хостинга, поэтому перед выводом из него убираются
управляющие символы и escape-последовательности: заголовок, который чистит экран, никто не
прочитает. «Идёт» значит «жив процесс прогона crewflow» —
номер процесса самого crewflow, а не исполнителя: crewflow живёт ровно столько, сколько идёт
прогон, и останавливает исполнителя вместе с собой, поэтому прогон, чей crewflow исчез, и
прерван, что бы ни делал его исполнитель. Номер процесса после перезагрузки может достаться
другому, поэтому сверяется и время старта. Состояние, записанное до этого, читается как
раньше: «идёт» без номера процесса — «прервана», если прошло больше таймаута исполнителя, иначе
«возможно, идёт».

## 7a. Запуск исполнителя без окна

Проверено на OpenCode 1.18.32 (сентябрь 2026):

- **stdin должен быть закрыт.** Без `< /dev/null` `opencode run` ждёт ввода и висит до таймаута.
  crewflow всегда запускает исполнителя с пустым stdin.
- **Вопрос о разрешении отклоняется автоматически**, прогон не зависает
  (`permission requested: external_directory (…); auto-rejecting`).
- **Отказ обрывает прогон с кодом выхода 0.** Первый настоящий прогон (crewflow#1) закончился
  сразу после отказа, без PR, работа осталась незакоммиченной в worktree. Код выхода успеха не
  означает: исход определяется по событиям и по тому, появился ли PR.
- **Проверяются и команды оболочки**, а не только файловые инструменты: `cat > /tmp/x` дал
  отказ `external_directory (/tmp/*)`. Поэтому исполнитель держит временные файлы внутри
  worktree (`.scratch/`, в `.gitignore`); сборка и тесты (`go test`, `t.TempDir()`) не
  затронуты — свои временные файлы инструменты создают сами.
- **Общий каталог git рабочей копии — вне её.** У `git worktree` объекты, ссылки и
  `info/exclude` лежат в `.git` основного клона. Обычные `git commit`/`git push` работают (путь в
  команде не упоминается), но явное обращение к `$(git rev-parse --git-common-dir)` отклоняется.
  Всё, что должно попасть в общий каталог (например, локальный игнор `.scratch/`), делает сам
  crewflow до запуска исполнителя, а не исполнитель.
- **Прерванный прогон продолжается той же сессией** (`opencode run --session <id>`), с тем же
  worktree и контекстом, а не начинается заново.

Поэтому:

1. Worktree задачи — это рабочая папка агента, всё внутри неё разрешено по умолчанию.
2. Доступ вне неё crewflow собирает из политики чтения (§7d) и выданных разрешений (§7e) и
   передаёт агенту способом этого агента (для OpenCode — конфиг разрешений в worktree или через
   переменную окружения), не трогая глобальные настройки человека. Руками этот список никто не
   ведёт.
3. crewflow читает поток событий агента (`--format json`) и лог; каждый автоматический отказ —
   это отдельный исход прогона: `blocked: permission external_directory <путь>`. Оркестратор видит
   его сразу и решает: разрешить путь в `crewflow.toml` и перезапустить или переформулировать
   задачу. Молча считать такой прогон удачным нельзя.
4. Таймаут прогона обязателен: зависание по любой причине превращается в исход `timeout`, а не
   в вечное ожидание.

### 7a.1. Самовосстановление по известной привычке

За 28–29.09.2026 прогоны пять раз обрывались на одном и том же: исполнитель пишет временный
файл в `/tmp` (`cat > /tmp/plan_test.go`), OpenCode отказывает (`external_directory /tmp/*`),
прогон заканчивается `blocked-permission`, и оркестратор вручную продолжает его одним и тем же
указанием «пиши в `.scratch/tmp`». Правило есть и в промпте, и в `AGENTS.md`, и в указаниях —
агент его всё равно иногда нарушает. **Правило не выполняется оттого, что его повторяют: одно
и то же указание пятый раз — это не контроль, а ручная работа.**

Поэтому crewflow отвечает на такой обрыв сам — **один раз, со стандартным указанием, в той же
сессии**:

| Причина отказа | Что это | Текст ответа |
|---|---|---|
| `tmp` | запись или чтение под `/tmp` или `/private/tmp` | временные файлы — в `.scratch/tmp` внутри worktree, тест для наблюдения — `zz_debug_test.go` в пакете и удалить его перед коммитом |
| `outside-cwd` | путь — соседний каталог worktree: `<worktrees>/<repo>/<другое имя>`, `cd ..` и относительный путь оттуда | работа задачи — внутри worktree; чужую папку — через subshell `(cd dir && …)` |
| `mention` | путь вне worktree встречается **только** внутри heredoc или строки команды `bash`, которая пишет файл в worktree (случай telecli#59, 29.09.2026) | править такие файлы инструментами `edit`/`write`, не скриптами |
| `other` | любой другой отказ | автопродолжения нет |

- **Продолжение одно и по списку.** Список — константа в коде (`internal/run/resume.go`), проект
  его не расширяет: расширение прав исполнителя не бывает следствием обрыва прогона, а `/tmp`
  остаётся закрытым (там чужие временные файлы и сокеты, доступ к которым — утечка).
- **Секрет — не привычка, а отдельный исход `blocked-secret`.** Форма привычки не делает отказ
  привычкой: команда, которая пишет файл в worktree и **читает** `~/.ssh`, отказана в той же
  форме, что и heredoc. Отказ, чей путь — или чья команда — касается места из списка запретов
  (§7d), заканчивает попытку как `blocked-secret` **чем бы ни закончилась сама попытка и что бы
  ни сказал классификатор привычек**. Путь сверяется со списком запретов в обеих записях (путь
  машины и путь от `~`), по паттернам `**/.env` и `**/.env.*` и с разрешением относительного
  пути от worktree, так что `../../../.ssh` — это тот же ключ, а `/private/var/…/.ssh` — то же
  место, что `/var/…/.ssh`. Путь, названный **только в тексте** команды, — тоже `blocked-secret`:
  команда не выполнилась, но доказать намерение нельзя, поэтому решение принимается «в отказ».
  Отчёт и журнал называют путь, вид доступа (`read`, `write`, `cd`, `named in text`) и
  `recovery: disabled`. Ни одна форма автопродолжения через это не проходит, и **после
  `blocked-secret` следующий прогон задачи crewflow сам не продолжает никогда** — что бы он ни
  был отказом.
- **Только когда все отказы попытки — из списка.** Хоть один отказ не из списка и не из
  запретов (например, `/opt/homebrew/include`) — автопродолжения нет: исход
  `blocked-permission`, решает оркестратор.
- **Один отказ — одна причина.** Отказы разных причин в одной попытке не отвечаются текстом
  одной из них.
- **Второй раз подряд по той же причине — не продолжает.** Исполнитель, которому сказали, где
  его scratch, и снова написал в `/tmp`, — это не привычка, которую можно вылечить указанием.
  Исход `blocked-permission`, решает оркестратор.
- **Ничего не меняется, кроме сообщения.** Продолжение идёт в том же worktree, в той же ветке и
  в той же сессии; номер попытки растёт, исход задачи — по последней попытке.
- **Каждое автопродолжение видно.** В журнал попытки пишется строка
  `crewflow: resumed once — <причина>`, в ответе `task run` — строка о том, что crewflow пошёл
  дальше сам, в состоянии задачи — отметка `auto_resumed` у попытки. По этому факту идёт и
  потеря «повтор без изменений» (§7j): попытка, которую crewflow продолжил указанием, повтором
  без изменений не считается.

Остальное — промпт. Правило временных файлов стоит **первым** пунктом правил прогона, с
примером (`.scratch/tmp/…`, `zz_debug_test.go` в пакете, удалить перед коммитом) и с тем, чем
кончается нарушение: отказ всегда обрывает прогон, пути назад нет.

## 7b. Если агента или модели нет

- `crewflow doctor` проверяет, что команда исполнителя существует и отвечает на короткую
  пробную задачу. Нет — понятное сообщение и что сделать.
- Если основной исполнитель недоступен (нет команды, кончились средства, ошибка провайдера —
  как в пробном прогоне: `Insufficient account funds` у одной из моделей), crewflow пробует
  исполнителей из `fallback` по порядку. Какой исполнитель выполнил задачу — пишется в PR.
- Замена исполнителя — новая попытка с новой сессией; сессию прежнего другой исполнитель не
  продолжает (контексты не смешиваются). `-continue` — только для того же исполнителя.
- Если не доступен ни один — задача остаётся открытой с исходом `blocked: no executor`, и
  оркестратор сообщает человеку. Выполнять задачу сам «вместо исполнителя» оркестратор без
  разрешения человека не начинает: это меняет, кто проверяет чью работу.

## 7c. Параллельные задачи

Worktree на задачу делает параллельность возможной; crewflow включает её, только когда она не
ломает проект.

- `[parallel] max_tasks` — предел одновременных прогонов (по умолчанию 1).
- **Задачи не должны пересекаться по файлам.** В задаче раздел «Границы» содержит список путей
  (glob), которые задача меняет. Две задачи идут параллельно, только если их списки не
  пересекаются; иначе вторая ждёт. Задача без списка путей идёт только одна.
- **Проверка по факту.** После прогона crewflow сравнивает реально изменённые файлы со
  списком; выход за границы — исход `blocked: out of scope`, до ревью не доходит.
- **Слияние всегда по одной.** Слияния идут строго последовательно; после каждого остальные
  одобренные PR, которые больше не fast-forward к `main`, перебазирует оркестратор, и они
  проходят ревью заново: rebase — новый SHA, одобрение не переносится (§7h).
- **Общие ресурсы проекта.** Ворота, которые нельзя запускать одновременно (тесты на одном
  порту, общая база, интеграция с реальным аккаунтом), помечаются `exclusive = true` и
  выполняются по одной, даже если задачи идут параллельно.
- Одна задача — один процесс исполнителя на свой worktree; два процесса над одним worktree
  запрещены.

## 7d. Окружение и зависимости

Агенту за пределами worktree может понадобиться одно из трёх, и решаются они по-разному.

| Что нужно | Пример | Как решается |
|---|---|---|
| Прочитать системные файлы | исходники зависимостей (`~/go/pkg/mod`), заголовки (`/opt/homebrew/include`), SDK | политика чтения, без участия человека |
| Инструменты пишут свои кэши | `go build` → `~/Library/Caches/go-build`, `npm` → `~/.npm` | это процессы сборки, а не файловые инструменты агента; разрешено |
| Поставить что-то в систему | `brew install`, `apt`, `pip install --user`, новая версия языка | агент не ставит никогда; см. ниже |

**Проект описывает потребности, а не пути.** `[requirements]` в `crewflow.toml` перечисляет
инструменты и команды проверки. `crewflow doctor` сверяет их до запуска; не хватает — понятное
сообщение и что поставить.

**Пути определяются сами: проект говорит, КАК их найти.** Таблица `[access]` в `crewflow.toml`
называет команды, а не папки: пути на машинах разные, а инструменты, у которых они спрашиваются,
уже знают ответ.

```toml
[access]
read_from = [["go", "env", "GOMODCACHE"], ["go", "env", "GOROOT"]]
read = ["/opt/homebrew/include"]   # постоянные пути, ~ раскрывается
```

Каждая команда печатает пути, по одному на строку, и у неё есть 10 секунд: инструмент, который не
ответил, не останавливает прогон. Пустые строки и несуществующие пути отбрасываются. Перед
запуском исполнителя crewflow выполняет эти команды на этой машине и отдаёт то, что осталось, —
**только на чтение**. Разрешение на чтение не даёт разрешения на запись: писать в эти папки по
прежнему нельзя, и то, что назвал проект, человек видит в ревью.

**Одно место — два написания.** Путь разбирается до самого длинного существующего префикса
(`EvalSymlinks` для той части, что есть, остальное присоединяется как написано) и попадает в
политику **обоими** написаниями, когда они разные: на macOS `/tmp` и `/var` ведут в `/private`,
и агент спрашивает о пути в том написании, в котором сам его написал, — правило в одном написании
не покрывает другое. Так и в списке запретов: `~/.ssh`, которой на машине может и не быть, должна
быть закрыта и как `/Users/kto/.ssh`, и как `/private/var/…/.ssh`.

**Запреты сильнее разрешений и зашиты в crewflow.** Секретные места закрыты всегда, даже если
проект назвал их или они попали внутрь разрешённой папки: `~/.ssh`, `~/.gnupg`,
`~/Library/Keychains`, `~/.config/gh`, `~/.aws`, `~/.netrc`, `~/.docker/config.json`, `~/.kube`,
`**/.env`, `**/.env.*`. Снять этот запрет проект не может. Кроме того, не открываются корень
диска, домашняя папка целиком и любой путь, внутри которого лежит место из списка секретов, — по
прямому пути или через симлинк. Каждый такой отказ — не ошибка прогона, а строка в
`crewflow doctor` и в журнале: агент читает то, что осталось, и получает отказ, если попросит
остальное.

**Попытка достать секрет — исход прогона, а не отказ среди отказов.** Если отказ касается места
из списка запретов, попытка заканчивается как `blocked-secret` — чем бы ни закончилась сама
попытка и какой бы причиной ни был отказ. Путь сверяется со списком запретов в обеих записях и
по паттернам, относительный путь разрешается от worktree, а путь, названный только в тексте
команды, считается достигнутым: команда не выполнилась, но доказать, что она не открыла бы
ключ, нельзя, поэтому решение принимается «в отказ» (§7a.1, §8). Отчёт и журнал называют путь,
вид доступа (`read`, `write`, `cd`, `named in text`) и `recovery: disabled`; автопродолжения нет
ни в какой форме, и следующий прогон задачи crewflow сам не продолжает.

**Как это доходит до агента.** Профиль агента (§7a) переводит политику в то, что его агент
понимает. У OpenCode три таблицы прав, и запретное место попадает во все три:

| Таблица | Что в ней |
|---|---|
| `permission.external_directory` | `<папка>/**: allow` для каждой разрешённой папки; для каждого запрещённого места — и само место, и `<место>/**` с `deny` |
| `permission.read` | те же запреты с `deny`: `external_directory` говорит только о путях снаружи worktree, а `.env` самого проекта внутри |
| `permission.edit` | те же пути, но `deny`, и для каждой открытой папки тоже: писать вне worktree нельзя никогда |

Само место в списке нужно рядом с `<место>/**`: секрет — часто файл, а не папка (`~/.netrc`,
`~/.docker/config.json`), и `**` под местом сам файл не покрывает.

Профиль `generic` получает `CREWFLOW_READ` и `CREWFLOW_DENY` — два списка путей через
`os.PathListSeparator`, для обёртки вокруг агента.

Если `OPENCODE_CONFIG_CONTENT` уже задан в окружении, crewflow разбирает этот JSON и дописывает
свои правила **по ключам** в каждую из трёх таблиц: правило прогона для его шаблона выигрывает,
а правило человека за любой другой шаблон и за любой другой инструмент остаётся. Значение, которое
не таблица шаблонов, а одно слово (`"edit": "deny"`), ключей не имеет и заменяется целиком.
Неразборчивый JSON — ошибка до запуска с понятным текстом: агент, которому
crewflow не смог сказать, что можно, не запускается.

**Политика чтения по умолчанию:**

- системные библиотеки, заголовки, SDK и кэши инструментов — читать можно, если проект назвал их
  в `[access]`;
- секреты — закрыты по умолчанию и открываются только разрешением (§7e): `~/.ssh`,
  `~/.gnupg`, `~/Library/Keychains`, конфиги с токенами (`~/.config/gh`, `~/.aws`, `~/.netrc`…),
  профили браузеров, `.env`;
- писать файловыми инструментами агента вне worktree нельзя.

`crewflow doctor` показывает, что именно разрешено читать на этой машине: строкой `access read` со
списком папок и строкой `access rejected` с отказами и причинами, а в `-json` — полем `access` с
`read`, `deny` и `rejected`. Первая строка журнала прогона — сама политика, с которой исполнитель
был запущен, а отказ от пути, который проект назвал, пишется на выход прогона.

**Если агент упёрся в отказ** (исход `blocked: permission <путь>`):

- путь только для чтения внутри системных корней из политики → оркестратор сам добавляет его в
  машинный список, пишет это в журнал и перезапускает задачу;
- всё остальное → вопрос человеку, один раз; ответ запоминается на этой машине.

**Если нужна зависимость**, агент заканчивает с исходом `blocked: needs <что> — <зачем>` и ничего
не ставит. Дальше: оркестратор показывает человеку готовую команду установки и выполняет её после
подтверждения, или проект работает в режиме `container`, где ставить можно.

### Изоляция: `[isolation] mode`

| Режим | Как | Подходит | Не подходит |
|---|---|---|---|
| `host` | обычный процесс, политика выше | любой проект | — |
| `sandbox` | средства ОС: macOS Seatbelt (`sandbox-exec`), Linux bubblewrap. Писать — только worktree и кэши; секреты закрыты на уровне ОС | большинство проектов, нативно и быстро | — |
| `container` | Docker/Podman или devcontainer; worktree монтируется внутрь; агент ставит что угодно внутри; образ и есть описание окружения | веб, бэкенд, Python, Node — всё, что собирается под Linux | проекты, которым нужна сама macOS (Keychain, cgo с системными фреймворками, `.dylib`) |

В `container` агенту внутрь нужны его ключи доступа к модели; они передаются только на время
прогона и не попадают в образ.

## 7e. Доступ к секретам и внешним системам

Главное правило: **прочитать секрет — значит отправить его провайдеру модели.** Всё, что агент
открыл, уходит в контекст модели. Поэтому секретами по возможности **пользуются, не видя их**.

Три уровня:

| Уровень | Как | Пример |
|---|---|---|
| 1. Пользоваться, не видя | команды через посредника, который держит секрет: `ssh-agent` (`SSH_AUTH_SOCK`), `gpg-agent`, `gh` с токеном в связке ключей | `ssh prod-1 'systemctl status app'` — приватный ключ агент не читает |
| 2. Читать конкретный файл | разрешение на путь, только чтение, на задачу или проект | `~/.ssh/config`, чтобы узнать имена хостов |
| 3. Действие с последствиями снаружи | агент **готовит** команду, человек **подтверждает**, после этого она выполняется | добавить SSH/GPG-ключ в GitHub, выкатить на сервер, удалить ресурс |

**Как это устроено:**

- `[[capabilities]]` в `crewflow.toml` объявляет, что проекту может понадобиться (`ssh` с
  хостами и файлами, `github-keys`, `deploy`…). Это видно в ревью.
- В задаче указано, какие возможности ей нужны; это часть Definition of Ready.
- Перед первым запуском с новой возможностью crewflow спрашивает человека: что именно, для
  какой задачи; варианты — на эту задачу / на проект / нет. Разрешение хранится в
  `~/.crewflow/grants/`, с областью и сроком, не в репозитории.
- Разрешение даётся на **файл или команду**, а не на папку: доступ к `~/.ssh/config` не открывает
  `~/.ssh/id_*`.
- Запись в чувствительные места — только **новых** файлов по точному пути, без перезаписи
  (например, `ssh-keygen -f ~/.ssh/id_ed25519_deploy`).
- Действия уровня 3 **всегда** требуют подтверждения в момент выполнения; разрешение «на проект»
  их не покрывает. Агент кладёт готовую команду в итог прогона, оркестратор показывает её
  человеку.
- Права внешних сервисов агент себе не расширяет. Пример: `gh ssh-key add` требует прав
  `admin:public_key`/`write:gpg_key`; расширить токен может только человек
  (`gh auth refresh -s …`, через браузер и 2FA).
- Журнал `~/.crewflow/audit.log`: какая задача, когда, каким разрешением воспользовалась.
  Без содержимого секретов.

**Без исключений закрыто:** чтение в модель приватных ключей, содержимого Keychain и токенов.
Для них есть посредники уровня 1. Если задаче действительно нужен сам секрет — меняется задача,
а не политика.

## 7f. Задача как ТЗ

Задача должна читаться человеком, чтобы он мог её контролировать. Поэтому issue состоит из
двух частей.

**1. ТЗ для человека** — на языке проекта (`project.language`), без ссылок на строки кода:

| Раздел | Что в нём |
|---|---|
| Зачем | какая проблема, одним-двумя предложениями |
| Что изменится | что человек увидит или сможет сделать после |
| Как проверить самому | шаги, которые можно повторить руками |
| Что не входит | чтобы не было сюрпризов |
| Риски и решения | развилки, которые оркестратор уже решил, и почему |

**2. Техническая часть для исполнителя** — ниже, свёрнута (`<details>`): критерии приёмки,
доказательство тестами, границы и пути файлов, нужные возможности (§7e).

**Одобрение ТЗ** — `[tasks] owner_approval`:

- `all` — каждая задача ждёт метки `approved` от человека;
- `risky` (по умолчанию) — ждут только рискованные: нужны секреты или внешние действия (§7e),
  установка в систему (§7d), изменение архитектуры или публичных интерфейсов, удаление данных.
  Оркестратор помечает такие задачи меткой `risky` и объясняет почему в «Рисках и решениях»;
- `none` — одобрение не требуется.

**Проверка готовности (DoR)** в `task run`: все разделы ТЗ заполнены, техническая часть
содержит критерии приёмки, тесты и пути; для задачи, которой нужно одобрение, стоит `approved`.
Иначе прогон не начинается, и crewflow говорит, чего не хватает.

**Отчёт в PR** тем же языком: «что сделано простыми словами» и «как проверить руками»; для
интерфейсных задач — снимок экрана.

**Команды:** `crewflow task show <N>` печатает человеческую часть в терминал;
`crewflow status` показывает, что ждёт одобрения, что в работе, что на ревью.

## 7g. Хостинг, трекер и CI — не только GitHub

В практике telecli GitHub играл три разные роли, и у каждой свои альтернативы. Поэтому это три
отдельных адаптера, а не один: связка «Bitbucket + Jira + Jenkins» иначе не собирается.

| Роль | Что делает для crewflow | Варианты |
|---|---|---|
| **Хостинг** (`[forge]`) | запросы на изменение, их голова и комментарии, слияние через API | GitHub, GitLab, Bitbucket, Gitea/Forgejo, Azure DevOps, `none` |
| **Трекер** (`[tracker]`) | задачи-ТЗ, метки `risky`/`approved`, закрытие | задачи хостинга (`forge`), Jira, Linear, `files` (задачи — файлы в репозитории) |
| **CI** (`[ci]`) | статус проверок на коммите | CI хостинга (`forge`), Jenkins, `command` (своя команда статуса), `none` (только локальные ворота) |

**Правила:**

- Ядро знает только общие понятия: задача, запрос на изменение, голова, комментарий, метка,
  статус проверок. Ни `gh`, ни «PR» в ядре нет.
- Адаптер работает штатным инструментом системы: `gh` (GitHub), `glab` (GitLab), `tea`
  (Gitea/Forgejo), `az repos` (Azure); где нормального официального CLI нет (Bitbucket, Jira) —
  REST API.
- Вход — за инструментом системы или связкой ключей (`gh auth`, `glab auth`, токен Jira в
  Keychain); crewflow токенов не хранит и не читает (§7e).
- Слияние по умолчанию — `git push` fast-forward, от хостинга не зависит. Если `main` защищён и
  вливать можно только через интерфейс, `merge.via = "forge"`: слияние через API хостинга, с теми
  же проверками (одобрен ровно текущий head, CI зелёный) и только fast-forward/rebase без
  merge-коммита, если хостинг это позволяет.
- Если у системы нет нужной возможности (например, урезанные issues в Bitbucket Cloud — задачи
  там обычно в Jira), адаптер говорит, чем она заменена, а `crewflow doctor` это показывает.
- `crewflow doctor` проверяет инструмент и вход для каждой настроенной роли, а не только `gh`.
- `kind = "none"` / `files`: задачи — файлы в `tasks/`, ревью — локальные ветки, ворота —
  локальные команды. Для офлайна, личных проектов и закрытых контуров.

**Порядок реализации** (решение владельца, 2026-09-28): GitHub в M1 (интерфейсы ролей
закладываются сразу, пока кода мало); затем **GitLab** — хостинг, трекер и CI в одном месте;
затем **Bitbucket + Jira**.

## 7h. Merge gate — отказ, которому можно доверять

Главная ценность crewflow — доказуемо безопасный путь «задача → исполнитель → PR → ревью
конкретного SHA → зелёный CI → fast-forward». Всё остальное наращивается поверх него.
Правила проверяются кодом, а не текстом задания. Это спецификация M2: интеграционные тесты
пишутся прямо по ней (IT-номера ниже).

### Что хранится и что вычисляется

Хранятся только факты процесса, в `~/.crewflow/state/<repo>/<N>.json`:

```json
{
  "schema": 1,
  "task": 43,
  "title": "…",
  "branch": "crewflow/43-…",
  "worktree": "~/.crewflow/worktrees/naghuale-crewflow/43",
  "profile": "opencode",
  "session": "…",
  "change": { "number": 44, "url": "…" },
  "attempts": [
    { "number": 1, "executor": "opencode", "session": "…", "identity": "owner",
      "started_at": "…", "ended_at": "…", "outcome": "pr-opened", "pid": 4242 }
  ]
}
```

- `schema` — версия формата; файл без неё читается как версия 0 и дописывается в новом.
  `identity` попытки — это режим (`owner` / `bot`); строка описания, которую видит
  человек, живёт в журнале и в отчёте о прогоне, а не в состоянии.
- Попытки называются `attempts` — так они назывались с M1, и переименование потеряло бы
  прогоны у всех, кто уже запускался. `merged_sha` и `verified_at` добавятся вместе со
  слиянием и сверкой (M2).
- У каждой попытки свой исполнитель, сессия и режим учётной записи (§7i). `-continue` после
  `changes requested` — новая попытка **той же** сессии того же исполнителя. Замена исполнителя
  (§7b) — новая попытка с новой сессией; сессия прежнего не продолжается.

### Откуда берутся факты

Gate ничего не знает о хостинге: он получает `Facts` и даёт `Verdict`. Собирает факты
`gate.Collect`, и всё, что он не смог узнать, — это `forge-unavailable` с объяснением, а
не «наверное можно»:

- **PR** — состояние, черновик, репозиторий, целевая ветка, голова, признак конфликта
  (`mergeStateStatus` хостинга, а не догадка о нём);
- **записи ревью** — комментарии PR вместе с `lastEditedAt`: правка после публикации
  видна, и запись, которую переписали, не считается;
- **обязательные проверки** — из правил ветки (protection и rulesets, оба) с запасным
  `[ci] required`; если хост не называет ни одной, обязательны все проверки головы, а
  если проверок нет вовсе — это тоже отказ, а не «значит, всё прошло»;
- **изменённые файлы** — файлы PR, а границы — из задачи (`Closes #N` в теле PR, иначе
  состояние прогона на этой машине);
- **история** — `git merge-base --is-ancestor` по настоящему git: голова и ветка
  проекта привозятся fetch'ем (refs/pull/N/head у GitHub), commit, которого в checkout
  нет, не предок ничему, а любая другая ошибка git — `forge-unavailable`.

Ревью работает **от лица владельца**, а не App'а исполнителя: правила ветки и запись
одобрения — права человека (§7i). Поэтому `crewflow review -approve` отказывается,
если логин `gh` не в `[merge] reviewers`: запись, которую gate не посчитает, лучше не
писать.

**Никогда не хранятся** «одобрено», «на ревью», «готово к слиянию». Они вычисляются заново из
хостинга и git непосредственно перед каждым действием, поэтому не могут разойтись с GitHub.
Статус задачи для человека (`task list`, `status`: «в работе», «на ревью», «одобрена», «готова
к слиянию», «влита», «сверена») — тоже вычисляемый.

### Запись ревью и кто может одобрить

Запись ревью — комментарий к PR, первая строка которого `REVIEW: APPROVED <полный sha>` или
`REVIEW: CHANGES REQUESTED`, дальше — машиночитаемый блок:

```
<!-- crewflow-review -->
decision: approved | changes_requested
commit: <полный sha>
task: <номер>
findings:
  - id: R1
    severity: blocking
    file: internal/…
    note: …
```

Запись пишет человек, руками или `crewflow review <PR> -approve` / `-request-changes <файл>`;
gate читает только первую строку, а блок нужен для того, кто читает запись программой.
`crewflow` пишет в блок решение, коммит и задачу, а текст замечаний кладёт над блоком —
разбор по пунктам (`findings:` с `severity`) пишет человек, когда хочет, чтобы о нём
читали отдельно.

Запись учитывается, только если:

- её автор — из `[merge] reviewers` в `crewflow.toml` (по умолчанию — владелец репозитория).
  Исполнитель может написать такой комментарий (у App есть право писать в PR), но gate его не
  считает — защищает не хостинг, а gate;
- комментарий не редактировался после публикации (иначе старую запись можно переписать задним
  числом);
- это **последняя** учитываемая запись ревью в PR: `CHANGES REQUESTED` после `APPROVED` отменяет
  одобрение.

```
approval_valid(pr) =
    последняя учитываемая запись == approved
    AND её commit == head PR
```

Достижимость одобренного SHA не входит в условие (при равенстве с head он достижим), она нужна
только чтобы **назвать причину** отказа: одобренный коммит — предок head → «после одобрения
добавлены коммиты» (`approval-stale`); не предок → «история переписана» (`history-rewritten`).

Rebase создаёт новый SHA, значит — новое ревью; одобрение через rebase не переносится. Rebase
запускает оркестратор (не исполнитель сам). Если после rebase ворота не проходят — исход
`blocked`, без автоматических попыток починить.

### Проверки перед слиянием

```
merge_ready(pr) =
    PR открыт                                  else pr-not-open
    AND не черновик                            else pr-draft
    AND репозиторий PR == project.repo         else wrong-repository
    AND целевая ветка == default_branch        else wrong-target-branch
    AND approval_valid(pr)                     else approval-missing | approval-untrusted |
                                                    approval-edited | approval-stale |
                                                    history-rewritten
    AND изменённые файлы (base..head) в границах задачи
                                               else out-of-scope
    AND обязательные проверки для head SHA:
          каждая есть                          else required-check-missing
          каждая завершена                     else required-check-incomplete
          каждая успешна                       else required-check-failed
          каждая от ожидаемого источника       else required-check-untrusted
          и относится именно к head            else ci-sha-mismatch
    AND удалённый default_branch — предок head else not-fast-forward
```

- Обязательные проверки берутся из правил ветки хостинга, а если их там нет — из
  `[ci] required`. Ожидаемый источник для GitHub — приложение GitHub Actions; отметку, выставленную
  кем-то другим через API статусов, gate не принимает.
- **PR с конфликтом не получает CI вовсе.** GitHub не запускает проверки для запроса,
  который нельзя слить (`mergeable_state: dirty`), и обязательные проверки просто не
  появляются. Поэтому конфликт — отдельный факт: gate называет его `not-fast-forward`
  с пояснением «конфликтует с main, нужен rebase», а не `required-check-missing`
  (найдено на PR #19, 29.09.2026).
- Границы проверяются и при слиянии, а не только после прогона: коммиты, добавленные позже, тоже
  могут выйти за границы. Снять `out-of-scope` может только владелец явной записью в PR
  (`SCOPE: ACCEPTED <sha> <причина>`), с теми же правилами автора и редактирования.
- Слияние только fast-forward, поэтому head PR и будущий `main` — один и тот же коммит: CI на
  head и есть CI на результате слияния, отдельная проверка результата не нужна.

Любая неопределённость (сеть, неполный ответ, неизвестное состояние) — отказ
`forge-unavailable` с объяснением. Отказ всегда называет одну причину из перечня ниже.

Затем push `<sha>:refs/heads/<default_branch>` без `--force` (аргументами, не строкой оболочки —
§10) и проверка по `git ls-remote`, что удалённая ветка указывает ровно на `<sha>`. Git отверг
push — `push-rejected` (если `main` успел уйти вперёд — `not-fast-forward`); после push ветка
указывает не туда — `verify-mismatch`. Код выхода `git push` итогом не считается.

### Причины отказа

| Причина | Когда |
|---|---|
| `approval-missing` | учитываемой записи ревью нет |
| `approval-untrusted` | единственные одобрения — от авторов не из `reviewers` |
| `approval-edited` | одобрение редактировалось после публикации |
| `approval-stale` | одобрен предок head: после одобрения добавлены коммиты |
| `history-rewritten` | одобренный SHA не предок head: история переписана |
| `pr-not-open`, `pr-draft` | PR закрыт или черновик |
| `wrong-repository`, `wrong-target-branch` | PR не в тот репозиторий или не в default_branch |
| `out-of-scope` | изменены файлы вне границ задачи |
| `required-check-missing` / `-incomplete` / `-failed` / `-untrusted` | обязательная проверка отсутствует / не завершена / упала / выставлена не тем источником |
| `ci-sha-mismatch` | зелёная проверка относится к другому SHA |
| `not-fast-forward` | default_branch не предок head (ушёл вперёд) |
| `push-rejected` | хостинг отверг push |
| `verify-mismatch` | после push удалённая ветка указывает не на одобренный SHA |
| `forge-unavailable` | хостинг или сеть не дали определённого ответа |

Повторный `merge`, когда default_branch уже содержит head, — не отказ, а итог `already-merged`
без изменений. Ошибка уборки после слияния (рабочая копия, ветка) — `merged-with-cleanup-warning`:
слияние состоялось, уборка — нет.

### Проверяемые обещания системы

crewflow обещает гарантии процесса, а не набор тестов. Под каждым обещанием — тесты, которые его
доказывают. Реестр живёт в коде (таблица тестов: обещание, номер, причина); мета-тесты сверяют его
с этим разделом и с перечнем причин отказа, чтобы обещание не ссылалось на несуществующий тест, а
причина отказа не осталась без проверки.

**1. После одобрения код нельзя незаметно подменить.**
IT-001 `approval-stale` · IT-002 `history-rewritten` · IT-005 `approval-edited`

**2. Слияние невозможно без настоящего одобрения.**
IT-003 `approval-missing` · IT-004 `approval-untrusted` · IT-006 замечания после одобрения отменяют
его

**3. Слияние невозможно при проблемах CI.**
IT-007 `ci-sha-mismatch` · IT-008 `required-check-missing` · IT-009 `required-check-incomplete` ·
IT-010 `required-check-failed` · IT-011 `required-check-untrusted`

**4. В основную ветку попадает только то, что в границах задачи и продолжает её историю.**
IT-012, IT-013 `not-fast-forward` · IT-014 `out-of-scope` · IT-015 `SCOPE: ACCEPTED` снимает отказ ·
IT-016 `pr-not-open`, `pr-draft` · IT-017 `wrong-repository`, `wrong-target-branch` · IT-018
`forge-unavailable`

**5. Владелец действительно видел результат** (для задач `owner-check`).
IT-024 `owner-acceptance-missing` (нет записи) · IT-025 `owner-acceptance-missing` (другой SHA) ·
IT-026 новый коммит отменяет приёмку · IT-027 `owner-acceptance-untrusted` · IT-028
`owner-acceptance-edited` · IT-029 приёмка текущей головы разрешает слияние

**6. Слияние действительно произошло — и ровно то.**
IT-019 удалённая основная ветка == одобренный SHA · IT-020 `already-merged` · IT-021
`merged-with-cleanup-warning` · IT-022 `push-rejected` · IT-023 `verify-mismatch`

**7. Ни одна причина отказа не остаётся без проверки.**
MT-001 каждая причина отказа из кода покрыта тестом · MT-002 каждый тест ссылается на существующую
причину · MT-003 реестр тестов в коде совпадает с этим разделом (обещания и номера)

Тесты полномочий (исполнитель пушит в default_branch, сливает через API) — в M3 (§7i), в режиме
`bot`; в режиме `owner` у исполнителя права владельца, и гарантию даёт только gate. Тесты прогона
(пустой результат, чужая рабочая копия) — уже в M1; восстановление и повторный `task run` — M4.

### Исполнение задачи — тоже под проверками кода

- `base_sha` фиксируется при запуске и записывается в состояние; рабочая копия создаётся от него;
- перед каждым опасным шагом: корень (`git -C <wt> rev-parse --show-toplevel`) == ожидаемая
  рабочая копия, репозиторий тот же, ветка — ветка задачи, default_branch не выписан в ней;
- после прогона — основная рабочая копия человека не изменилась.

**Идемпотентность (M4):** повторный `task run` при существующем PR не начинает заново; повторный
`review` не дублирует запись; потерянная рабочая копия восстанавливается из ветки и PR.

## 7i. Разделение полномочий

Сейчас (пилот) оркестратор и исполнитель ходят в GitHub под одним аккаунтом владельца, и
исполнителя сдерживают только слова задания. Так нельзя: разделение должно быть архитектурным.

Решение владельца (2026-09-28): **исполнитель работает через GitHub App**.

| | Исполнитель (GitHub App) | Оркестратор (владелец / его вход) |
|---|---|---|
| Читать задачи и код | да | да |
| Пушить | только ветки `crewflow/*` | — |
| Создавать и обновлять PR | да | да |
| Писать запись ревью, одобрять | нет | да |
| Пушить в default_branch, сливать | **нет** (правила ветки) | да, только через merge gate |
| Менять правила ветки, обязательные проверки | нет | владелец вручную |
| Закрывать задачу как выполненную | нет | закрывается слиянием (`Closes #N`) |

- Права App: Contents — read/write, Pull requests — read/write, Issues — read, Metadata — read.
  Без Administration и без Workflows.
- Правила (ruleset) на default_branch: изменение — только в обход для владельца; App в список
  обхода не входит. Так даже при ошибке или обходе задания исполнитель физически не может
  запушить в `main`.
- Ключ App хранится в Keychain; crewflow сам выписывает короткоживущий (≤ 1 ч) токен
  установки для одного репозитория и передаёт исполнителю только его (`GH_TOKEN` и помощник
  учётных данных git для этой рабочей копии). Ключ App исполнитель не видит. Токен исполнителю
  виден (он в его окружении) — поэтому он короткоживущий и с минимальными правами.
- Правило ветки на `crewflow/*`: force push и удаление запрещены; обход — только у владельца.
  Rebase задачи поэтому делает оркестратор под входом владельца (§7h), App переписать историю
  ветки не может.
- Оркестратор работает под входом владельца (`gh auth`).
- Дополнительно, как защита от случайности: хук `pre-push` этой задачи отклоняет пуш
  куда-либо кроме её ветки. Папка хуков принадлежит только рабочей копии этой задачи
  (`core.hooksPath` на уровне рабочей копии), поэтому чужие рабочие копии того же
  репозитория — ревью оркестратора, копия человека — пушат что хотят.
- Для хостингов без приложений (GitLab, Bitbucket) — аналог: отдельный бот-пользователь с
  токеном проекта и защищённой веткой (§7g).

### Два режима, и режим всегда виден

Настроить App — работа, а для личного проекта она лишняя. Поэтому режимов два, и
нынешний остаётся по умолчанию: `[identity] mode = "owner"` — вход владельца, ничего
настраивать не надо; `mode = "bot"` — отдельная учётная запись хостинга. Подтаблица
бота — своя у каждого хостинга (`[identity.github_app]`), а слово режима одно.

Одна строка — `исполнитель: bot — GitHub App crewflow-executor (установка 12345)` или
`исполнитель: owner — вход gh naghuale (общие права)` — печатается везде, где человек
смотрит на прогон: в `crewflow doctor` (и в `-json` полями `identity.mode` и
`identity.description`), первой строкой отчёта `task run` и заголовком `task watch`,
столбцами `AS` (от чьего имени) и `EXECUTOR` (какой ИИ-агент) в `task list`, первой записью
журнала прогона и полем `identity` у
каждой попытки в состоянии задачи. По журналу и состоянию видно, от чьего имени шла
каждая попытка, а не только последняя. В режиме `owner` `doctor` пишет предупреждение:
права исполнителя — это права входа.

Трекер задач может ходить под своей учётной записью отдельно от хостинга кода; строка
`трекер: …` появится вместе с поддержкой Jira (M8), пока трекер — тот же GitHub.

### Как это устроено в коде

Ядро знает только два слова — `owner` и `bot`. Как выписать учётные данные бота, решает
роль хостинга (`internal/forge/roles`): `ExecutorIdentity(ctx) (Identity, error)`, где
`forge.Identity{Mode, Description, Env, GitConfig, Secrets}` — `Secrets` это значения,
которые вымарываются из журнала. Так Bitbucket и GitLab добавляются своей реализацией
без правки ядра, а файл проекта без подтаблицы бота для своего `forge.kind` отвергается
при чтении настроек, а не в середине задачи.

- `internal/secret` — хранилище: `Store{Get, Set}` (и `Has` там, где хранилище умеет
  сказать о наличии, не читая), сервис `crewflow`, аккаунт `github-app-<app_id>`.
  Реализация для macOS — сам Security.framework через cgo (`SecItemAdd` /
  `SecItemUpdate` / `SecItemCopyMatching`, класс `kSecClassGenericPassword`): ключ
  пишется и читается байтами, ничего не спрашивается на терминале, ничего из ключа не
  попадает в аргументы, которые видны в `ps`. Программа `security` для этого не годится:
  `add-generic-password -w` спрашивает значение на своём терминале, читает одну строку
  (PEM — много) и отдаёт непечатаемое в виде hex-дампа. На других ОС и на macOS без cgo —
  «хранилища нет», и режим `bot` об этом говорит. Ни один тест не открывает связку
  ключей: работа с ней за интерфейсом, в тестах подделка, а тест-страж смотрит на тесты
  пакета и пропускает ровно два способа дойти до настоящей связки — файл, собираемый там,
  где связки нет, и тест, пропущенный без `CREWFLOW_KEYCHAIN_TEST=1` (его переменную не
  ставит ни CI, ни прогон; вручную его запускает владелец: он пишет в связку ключей под
  случайным именем, читает, перезаписывает и удаляет).
- `internal/forge/github/app` — JWT RS256 (iat − 60 с, exp + 9 мин, iss = app_id) на
  стандартной библиотеке и обмен на токен установки
  `POST /app/installations/{id}/access_tokens` с `repositories: [<repo>]` и правами из
  таблицы выше; время жизни — из ответа. HTTP-клиент подставляемый.
- `crewflow auth app import <файл.pem>` кладёт ключ в связку ключей и ничего из ключа не
  печатает; `crewflow auth app check` говорит, что ключ есть, установка найдена и какие
  у неё права. Токен не печатает ни одна из этих команд.
- `task run` в режиме `bot` выписывает токен и передаёт исполнителю `GH_TOKEN`,
  `GIT_AUTHOR_*` и `GIT_COMMITTER_*` бота (`<slug>[bot]`,
  `<id>+<slug>[bot]@users.noreply.github.com`); в рабочей копии ставит
  `credential.helper = crewflow auth git-credential` (настройка только этой копии) и
  `core.hooksPath` на папку `~/.crewflow/hooks/<owner-repo>/<N>` с одним `pre-push` для
  ветки этой задачи. В общую папку хуков репозитория crewflow не пишет никогда: она одна
  на все рабочие копии, и чужой `pre-push` человека перетирать нельзя. Папка хуков уходит
  вместе с рабочей копией задачи. Если после прогона ветка запушена, а PR нет, crewflow
  открывает PR свежим токеном, и исход — `pr-opened`.
- Ключ и токен не попадают ни в журнал, ни в `.err`, ни в вывод, ни в сообщения ошибок:
  значения из `Secrets` заменяются в журнале на `[redacted]`.

Правила ветки на хостинге остаются за владельцем: crewflow их не создаёт и не меняет
(§8.5) — это ручной шаг настройки проекта, и `doctor` говорит, что без них режим `bot`
не даёт обещанного.

## 7j. Показатели процесса и ресурсы CI

**Метрики объясняют, где процесс теряет качество, время или ресурсы. Метрики не ранжируют агентов.**
Метрики нужны не для оценки участников, а для выбора следующей меры контроля:
журнал → показатели → главная потеря → мера контроля → решение человека.
Вывод по умолчанию диагностирует («процесс здоров?»), подробный — расследует. Если человек не
понимает, что значат цифры, их слишком много.
Хранятся только факты; каждый показатель, оценка и предупреждение вычисляются при запросе и
нигде не записываются (как одобрение в §7h). Источники фактов: журнал задачи (события попыток,
указания — #18), записи ревью с находками (§7h), записи слияния и сверки, связи задач
(`Fixes-task: #N`), данные хостинга о CI.

### Основные формулы

| Показатель | Формула |
|---|---|
| круги ревью (Review rounds) | число записей ревью задачи до одобрения включительно, минимум 1: медиана, среднее, максимум |
| с первого раза (First pass) | задачи с одним кругом ревью / задачи, у которых есть хотя бы одна запись ревью |
| доля ушедших дефектов | влитые задачи, у которых есть задача-исправление с `Fixes-task: #N` / влитые задачи — только задачи, влитые не позже чем `[stats] settle_days` (7) дней назад: у вчерашней задачи исправление ещё не успело появиться; окно пишется рядом с цифрой |
| без исправлений после слияния (First merge accuracy) | `1 − доля ушедших дефектов` — та же величина, не считается отдельно |
| отдача ревью (Review yield), по уровню | исправленные замечания уровня / все замечания уровня; уровни `blocking`, `medium`, `cosmetic` |
| обрывы | попытки с исходом `blocked`, `blocked-permission`, `timeout`, `out-of-scope`, `executor-failed`, `no-change-request` — по видам; доля обрывов = такие попытки / все попытки |
| доведено | влитые / начатые |
| восстановление | влитые после хотя бы одной неудачной попытки / задачи с неудачной попыткой |
| время агента | сумма длительностей попыток задачи |
| время до слияния | от начала первой попытки до слияния, медиана |
| ожидание | оркестратора: от конца попытки до записи ревью или указания; владельца: от события «нужно от человека» до его выполнения |

Замечание **исправлено**, если в журнале есть цепочка: запись ревью с замечанием `Ri` →
попытка с тем же `Correlation` → следующая запись ревью без `Ri`. «Предотвращённый дефект» не
утверждается — это ненаблюдаемо.

Ушедший дефект засчитывается **каждой роли**, через которую прошёл: исполнителю, оркестратору,
одобрившему коммит, владельцу, принявшему сборку (если была приёмка).

### Сложность задачи

Оценивает задачу до начала работы, а не качество её выполнения — иначе худшая работа
делала бы задачу «сложнее» и смягчала оценку. Замечания ревью и число строк не входят.

```
критерии приёмки     1–3 → 1   4–7 → 2   8+ → 3
пути в «Границах»    1 → 1     2–4 → 2   5+ → 3
риск                 обычная → 0   risky → 2
возможности (§7e)    нет → 0   внешнее действие → 1   секрет → 2   архитектура → 2
реализация           1 + log2(изменённых файлов + 1)
```

Сумма — сложность; до 5 — малая, 5–8 — средняя, 8–11 — большая, больше — очень большая.
Веса и пороги — `[stats]` в `crewflow.toml`.

### Надёжность — одна вторичная цифра

```
надёжность = с_первого_раза × (1 − доля_ушедших_дефектов) × (1 − доля_обрывов)
```

Каждая доля взвешена сложностью задач: `Σ(признак × сложность) / Σ(сложность)`; доля обрывов
считается по попыткам, и каждая попытка получает вес своей задачи. Показывается
только рядом с исходными показателями.

### Малые выборки

Если в разрезе меньше 10 задач (`[stats] min_tasks`), доли показываются дробью с пометкой —
`8/13 — insufficient data`, — без процентов; надёжность не показывается.

### CI как ограниченный ресурс

**Откуда это правило.** 29.09.2026 закончились минуты GitHub Actions аккаунта: 2000 из 2000 в
месяц. Их съел приватный telecli: за сентябрь 104 прогона CI (310 задач в них); чистого времени
Linux — 409 мин, macOS — 123 мин, но macOS считается ×10, и к оплате ушло ≈ 1640 мин — **три
четверти на macOS**; ≈ 1060 из них — прогоны в PR, то есть на доработки: CI шёл на каждый push
каждой попытки. crewflow этого не видел: проверки PR падали за секунды без логов и выглядели как
ошибка в коде; о лимите узнали из письма GitHub. Вывод: **бездумно гонять CI — не результат.**
Правильный процесс следит за расходом до запуска, потому что у хостингов есть лимиты, и у каждого
свои (ориентиры бесплатных планов на сентябрь 2026 — проверять у хостинга: GitHub Actions — 2000
мин в месяц для приватных репозиториев, публичные бесплатны; GitLab — вычислительные минуты;
Bitbucket Pipelines — минуты сборки; множители у дорогих раннеров).

В приватном проекте CI — ограниченный ресурс; он планируется до запуска, как бюджет модели.
Модель общая для любых платных раннеров (адаптеры отдают `used`, `included`, `resets_at`,
видимость репозитория).

- **Квота аккаунта** — минуты хостинга, общие для всех приватных репозиториев аккаунта; пороги
  `warn_at`, `restrict_at`, `stop_at` считаются по ней.
- **Бюджет проекта** — `budget_minutes` или `budget_share` (% квоты): сколько аккаунт даёт
  этому проекту.
- **Стоимость прогона** = средняя длительность последних прогонов по задачам × множитель
  раннера (Linux 1, Windows 2, macOS 10 — по документации хостинга).
- **Полезный прогон** — на коммите, который дошёл до записи ревью или до слияния.
  **Лишний** — на коммите, заменённом до ревью, отменённый, на черновике или в PR, не
  дошедшем до ревью. Минуты делятся на полезные и лишние только по этим фактам.
- Нет данных — `unknown`, без оценок.

### Главная потеря и мера контроля

Все потери переводятся в одну единицу — потерянные минуты работы, — и каждая считается только
по фактам журнала за период:

| Потеря | Потерянные минуты |
|---|---|
| обрывы, по видам (`blocked-permission`, `timeout`, `out-of-scope`, `executor-failed`, `no-change-request`, `blocked`) | длительность оборвавшихся попыток + ожидание до следующей попытки |
| переделки | Σ длительность попыток, запущенных замечаниями ревью (`Correlation` записи ревью); первая попытка задачи в потери не входит |
| повтор без изменений | Σ длительность попыток, закончившихся тем же исходом по той же причине, что и предыдущая попытка той же задачи, без указания оркестратора и без правки `crewflow.toml` между ними |
| ушедшие дефекты | время агента + время ревью + время владельца (приёмка) на задачах-исправлениях (`Fixes-task: #N`) |
| ожидание, по ролям | ожидание владельца и оркестратора |

**Попытка, которую crewflow продолжил сам, повтором без изменений не считается** (§7a.1): между
ней и предыдущей было указание — то самое, текст которого лежит в коде, — и потеря «повтор без
изменений» меряет повторы, где не изменилось ничего, включая слова. Иначе каждое
самолечение выглядело бы в статистике как потеря, а мера, которая потеря убирает, платила бы за
себя дважды. Продолжение без отметки об этом (указания не было) — повтор без изменений, и
считается как есть.

Главная потеря — наибольшая, с двумя правилами:

1. **Потери качества важнее потерь времени** (инвариант): если доля ушедших дефектов не меньше `[stats] quality_floor`
   (10 %), главная потеря — ушедшие дефекты, независимо от минут.
2. **Мелочь не показывается:** если наибольшая потеря меньше 10 % времени агента за период —
   `no significant loss`.

Строка: что, сколько раз и сколько времени — `5 runs blocked on permissions — 1h 40m`.

**Если видим проблему — усиливаем контроль там, где она.** К главной потере всегда предлагается
мера; включается она только с согласия владельца:

| Главная потеря | Мера контроля |
|---|---|
| обрывы на правах | добавить в `[access]` пути, на которых обрывались попытки (crewflow их перечисляет) |
| таймауты | увеличить `executor.timeout` или делить задачи мельче |
| выход за границы | `task check` предупреждает о путях, которые задачи этого вида забывали (`go.mod`, `docs/**`) |
| переделки | для задач этого вида (метка, пути) — обязательная приёмка владельцем и правило «данные, как у источника» |
| ушедшие дефекты | для путей, где они были, — обязательная приёмка владельцем и регрессионный тест в критериях приёмки |
| ожидание владельца | всё, что ждёт человека, — одной сводкой, а не по одному |
| повтор без изменений | повторный запуск задачи после обрыва — только с указанием или правкой настроек; иначе `task run` предупреждает и называет прошлую причину |

Если одна и та же потеря главная два периода подряд, crewflow пишет в журнал событие «нужно
решение владельца» с готовой правкой `crewflow.toml` (#18). Меры не включаются сами: изменение
правил — решение владельца.

### Что показывается по умолчанию

`crewflow stats` отвечает на три вопроса — хорошо ли идут задачи, где главная потеря, хватит
ли ресурсов — не больше чем семью строками:

```
crewflow · last 30 days · 13 merged of 18 started

First pass            7/13     approved at the first review
Clean after merge    11/13     no fix needed after the merge
Review rounds           1.8    median 1
Time to merge          46m     median

Biggest loss       5 runs blocked on permissions — 1h 40m
  control          add ~/go/pkg/mod to [access] read_from
CI                   91 %      of the account's minutes — economy recommended
```

**Главная потеря** — одна строка и мера контроля к ней (выше). Лишние минуты CI сюда не входят:
это другой ресурс, он в строке CI. Строка **CI** — только для приватного репозитория и при расходе от
`warn_at`. Всё остальное — `-details`, `-by executor|model|project|orchestrator|owner`,
`-json`.

## 7k. Матрица ответственности

Кто что может и **кто это держит**: инструмент исполнителя (OpenCode), crewflow, правила хостинга
или только дисциплина участника. Последнее — места, где ещё доверие к человеку вместо проверки
кодом; каждое такое место — кандидат в задачу. Роли: **исполнитель** (агент без окна; режим `bot`
— от имени App, `owner` — под входом владельца), **оркестратор** (под входом владельца `gh`),
**владелец**, **crewflow**.

### Зоны доступа исполнителя к файлам

| Зона | Что | Доступ | Кто держит |
|---|---|---|---|
| 🟢 зелёная | рабочая папка задачи, её `.scratch/tmp` (`TMPDIR`) | чтение и запись | OpenCode (worktree — рабочая папка агента) |
| 🟡 жёлтая | зависимости и инструменты, названные проектом (`[access] read_from`: кэш модулей, GOROOT, SDK, заголовки) | только чтение | crewflow → правила OpenCode (§7d) |
| 🔴 красная | секреты: `~/.ssh`, `~/.gnupg`, `~/Library/Keychains`, `~/.config/gh`, `~/.aws`, `~/.netrc`, `~/.docker/config.json`, `~/.kube`, `.env`, `.env.*` (в обоих написаниях путей) | никогда; попытка — исход `blocked-secret`, без самовосстановления | crewflow → правила OpenCode; инвариант §8 |
| — всё остальное | `/tmp`, чужие рабочие папки, копия человека, настройки и данные программ | отказ; `/tmp` и выход через `cd` — одно автопродолжение (crewflow#26) | OpenCode |

Установка в систему (`brew`, `pip`, языки) — исполнитель никогда: исход `blocked: needs …`, решение
человека.

### Хостинг (GitHub)

| Действие | Исполнитель `bot` | Исполнитель `owner` | Оркестратор | Владелец |
|---|---|---|---|---|
| push ветки своей задачи | да | да | да (rebase) | да |
| push в чужую ветку задачи | нет — хук `pre-push` | ⚠ можно технически | да | да |
| push в default_branch | нет — правило ветки + хук | ⚠ можно технически | только одобренный SHA fast-forward (§7h) | да |
| force push в `crewflow/**` | нет — правило ветки | ⚠ как владелец | да (обход администратора) | да |
| открыть PR | да | да | да | да |
| запись `REVIEW: APPROVED` | пишет, не засчитывается gate (не доверенный автор) | ⚠ засчитывается — тот же вход, что у владельца | да | да |
| запись `ACCEPTED` (приёмка) | не засчитывается | ⚠ см. ниже | ⚠ см. ниже | да |
| изменить CI (`.github/workflows`) | нет — у App нет права Workflows | ⚠ можно технически | да | да |
| настройки репозитория, правила веток | нет | нет | только с согласия владельца | да |
| слить собственный документ оркестратора | — | — | нет — вливает владелец | да |

Правила веток есть только у публичных репозиториев (на бесплатном плане); у приватного
default_branch от бота держит лишь хук `pre-push`.

### Решения

| Решение | Кто принимает | Кто держит |
|---|---|---|
| одобрить `risky`-задачу (`approved`) | владелец | ⚠ метку ставит оркестратор по словам владельца |
| одобрить код | оркестратор | gate: доверенный автор, без правок, ровно голова (§7h) |
| приёмка сборки (`owner-check`) | владелец | ⚠ запись `ACCEPTED` пишет оркестратор по словам владельца |
| слияние | оркестратор | gate (§7h), правило ветки |
| обход правила (`RULE-WAIVED`) | владелец | gate: доверенный автор |

### Где ещё доверие вместо проверки

1. **Оркестратор и владелец — один технический субъект.** Оркестратор работает под входом
   владельца, поэтому `APPROVED`, `ACCEPTED`, `approved` и `RULE-WAIVED` на хостинге подписаны
   одним логином; gate отличает бота от человека, но не оркестратора от владельца. Разделение
   учётных записей — crewflow#31.
2. **Исполнитель в режиме `owner`** технически может всё, что владелец. Режим `bot` — для любой
   работы, где это важно; `crewflow doctor` предупреждает.
3. **Приватный репозиторий без правил веток** держит default_branch только хуком `pre-push`.

## 8. Инварианты безопасности

1. Исполнитель работает только в своём worktree; рабочая папка человека не меняется никогда.
2. Слияние — только fast-forward, только одобренного sha, только при зелёном CI. `--force` нет.
3. Одобрение относится к конкретному коммиту; новый коммит требует нового ревью.
4. crewflow не хранит и не печатает секреты; команды ворот получают окружение как есть.
   Секреты не читаются в модель; ими пользуются через посредников (§7e).
5. Необратимые действия вне цикла (удаление веток, переписывание истории, изменение настроек
   репозитория) crewflow не делает.
6. Если исполнитель вернулся без PR, с упавшими воротами или по таймауту — это исход прогона, а
   не повод повторять молча: оркестратор решает, что дальше.
7. Агент не ставит ничего в систему хоста и не расширяет себе права внешних сервисов; действия
   с последствиями снаружи — только после подтверждения человека (§7d, §7e).
8. Одобрение и готовность к слиянию не хранятся — вычисляются из хостинга и git перед каждым
   действием; одобрение считается только от доверенного автора и без правок после публикации.
9. У каждой попытки ровно один исполнитель и своя сессия; замена исполнителя не продолжает чужую
   сессию.
10. Ветки задач защищены от force push правилами хостинга (предотвращение), а gate отличает
    переписанную историю от новых коммитов (обнаружение, `history-rewritten`). Нужны оба.
11. Каждый отказ gate называет одну причину из перечня §7h; неизвестность — отказ.
12. Исполнитель работает либо как вход владельца, либо как отдельная учётная запись
    хостинга, и какой из двух — сказано в `doctor`, в отчёте прогона, в его журнале, в
    состоянии задачи и в списке прогонов (§7i). Молчаливого режима нет: отчёт, который
    не называет полномочия прогона, неполон.
13. Каждый ушедший дефект оставляет после себя новый контроль — тест, проверку gate или пункт
    приёмки (задача-исправление: `Fixes-task: #N` и `Control: …`); без него урок не закрыт
    (`lesson-unclosed`, §10).
14. Попытка дотянуться до секрета всегда останавливает прогон — чем бы ни закончилась сама
    попытка, какой бы причиной ни был отказ и что бы ни сделало самовосстановление (§7a.1, §7d).
    Исход `blocked-secret`, автопродолжения нет, а после него следующий прогон задачи crewflow
    сам не продолжает: то, что человек должен увидеть, не решается указанием агента.

## 9. Связь с Claude Code

- `crewflow init` добавляет в `CLAUDE.md` проекта короткий раздел с ролью оркестратора и циклом.
- Skill `crewflow` для Claude Code: когда вызывать какие команды, как писать задачу по шаблону,
  как читать `--json`, когда звать человека.
- Человека зовут на: архитектурные развилки, спорные компромиссы, необратимые шаги, исчерпанные
  попытки. Всё остальное оркестратор ведёт сам.

## 10. Уроки

Два уровня:

- **Общие** — в `crewflow/protocol/LESSONS.md`: не верить самоотчёту; worktree вместо общей
  папки; детерминированные тесты вместо пауз; сверять API со схемой, а не по памяти;
  проверять «тем же путём, что программа»; одобрение привязано к sha; и уроки aiac.
  Из пилота: тесты исполнителя писали в настоящий `~/.crewflow`, а потом исполнитель попытался
  убрать за собой `rm -rf` в реальном домашнем каталоге — эту команду остановил автоматический
  отказ «вне рабочей копии» (§7a). Отсюда два правила: тесты подменяют домашний каталог целиком
  (`TestMain` + `t.TempDir()`), а политика «вне рабочей копии — только с разрешения» — не помеха,
  а главная защита режима `host`.
- **Проектные** — в самом проекте (`docs/LESSONS.md`): для telecli это схема TDLib, отметки
  символами в режиме без цвета и т. п.

- **CI — ограниченный ресурс, а не бесплатная проверка (29.09.2026).** Приватный telecli за
  месяц исчерпал 2000 минут GitHub Actions: CI на каждый push каждой доработки, macOS ×10 — три
  четверти расхода. crewflow не видел ни расхода, ни причины упавших проверок. Отсюда §7j «CI как
  ограниченный ресурс»: видимость репозитория, квота аккаунта, бюджет проекта, прогноз до запуска,
  режим экономии, причина `ci-quota-exhausted` (crewflow#22).

- **Промахи оркестратора (28–29.09.2026) — и правила, которые из них вышли.** Оркестратор тоже
  ошибается; процесс должен ловить и его ошибки, а не только ошибки исполнителя.

  | Промах | Что поймало | Правило |
  |---|---|---|
  | Одобрил telecli#68 (статус отправки): тесты зелёные, описание убедительное, но тесты проверяли обработчик по отдельности, а не живую цепочку; в программе статус так и остался «Sending». | приёмка владельца до слияния | Для задачи, которая работает с живыми данными или событиями внешней системы, одобрение требует теста через настоящую проводку программы (не одного компонента) на записанной последовательности событий; иначе — `changes requested`. |
  | Одобрил telecli#52 и crewflow#3: тестовые данные (TDLib, GitHub) были придуманы, а не взяты у источника; дефекты ушли в main (#53, #13, #15). | владелец на живом аккаунте, после слияния | Данные и запросы внешнего источника в тестах — в том виде, как их отдаёт источник (#9); ревью проверяет происхождение фикстур. |
  | Сказал владельцу «App установлен только на crewflow», не проверив; было неверно. | владелец | Утверждение о внешней системе — только после проверки командой (`crewflow doctor`, API); иначе говорить «не проверял». |
  | Дал владельцу команду `printf … > config.toml`, которая перезаписала бы весь файл настроек. | владелец не выполнил | Команды для человека, которые пишут в его файлы, — только дописывающие (`>>`) или через команду программы (`configure set`); перед советом прочитать, что в файле уже есть. |
  | Запустил тесты с поддельным HOME и пробу `security` — на Mac владельца появились окна связки ключей и пробная запись в login. | владелец увидел окна; запись найдена и удалена | Ничего, что касается связки ключей, не запускается на машине владельца; такие тесты — только в CI или по явному запросу владельца. |
  | Неверно составил ТЗ: «чужие сообщения без фона» (telecli#59), «-all» без учёта занятого флага (crewflow#10), «EXECUTOR» для режима входа. | владелец при приёмке; ревью | ТЗ интерфейса сверять с образцом, который видит человек (макет, скриншот эталонной программы); флаги и имена — сверять с тем, что уже есть в коде. |

  **Инвариант: каждый ушедший дефект превращается в новый тест, новую проверку gate или новый
  пункт приёмки — иначе урок не закрыт** (задача-исправление несёт `Fixes-task: #N` и
  `Control: …`; доля закрытых уроков — в статистике, §7j). Правила из таблицы проверяются кодом
  (crewflow#29), а не только записаны здесь.

  Общее: промахи оркестратора ловили приёмка владельца и живая проверка — поэтому приёмка до
  слияния (#9) и проверка по фактам, а не по описанию, обязательны и для работы оркестратора.
  Промахи оркестратора учитываются в статистике по роли (§7j, «ушедшие дефекты по ролям»).

**Критерий фокуса.** Задача относится к ядру, только если без неё перестаёт работать путь одной
задачи:

```
Issue → Run → PR → Review → Approval(SHA) → Merge → Verify
```

вместе с разделением ролей. Задача, после удаления которой этот путь целиком сохраняется, не
попадает в текущую веху ядра: она идёт в `v1.1` (воспроизводимость и восстановление) или получает
метку `later` (наблюдаемость и удобство — статистика, бюджет CI, показ прав). Вехи на хостинге:
`v1` — безопасный путь одной задачи с разделёнными ролями (#26, #8, #9, #31); `v1.1` — уроки как
контроли, журнал задачи, `init`, восстановление, `status` (#29, #18, M4); `later` — #21, #22, #32.
Опасность, которую критерий закрывает: идеальный отчёт о качестве процесса при ещё небезопасном
слиянии.

**Приоритет — M2 и M3.** M6 и дальше не начинаются, пока merge gate и разделение полномочий не
покрыты интеграционными тестами (§7h, §7i).

Пока не делать (до надёжного пути одной задачи): DAG и волны задач, постоянные роли агентов,
дашборд, своя БД, автоматическое разрешение конфликтов и rebase, squash, своя очередь слияний,
выбор «лучшего» из нескольких результатов, генерация задач из большой идеи.

## 12. Открытые вопросы

- Лицензия (aiac — Apache-2.0; если заимствуем тексты уроков, нужна ссылка и NOTICE).

- Можно ли вместо обрыва прогона после отказа получить продолжение работы (настройка OpenCode
  или ответ через `--attach` к серверу) — проверить на M1.
