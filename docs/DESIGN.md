# crewflow — устройство

Статус: **черновик на согласование**.

## 1. Зачем

crewflow — небольшой фреймворк для разработки связкой двух агентов:

- **оркестратор** (Claude Code) ставит задачи, проверяет результат и решает, что вливать;
- **исполнитель** (по умолчанию OpenCode) пишет код и тесты по одной задаче за раз.

Цель — чтобы цикл «задача → код → ревью → слияние → проверка» шёл сам, без ручной
передачи сигналов, открытых окон и подталкиваний, а человек участвовал только в решениях.

Фреймворк **не зависит от проекта**: язык, стек, команды сборки и проверок, соглашения —
всё задаётся настройками. Первым проектом, на котором его обкатывают, был telecli (Go + TDLib),
но ни одна его деталь не зашита в ядро.

## 2. Откуда идеи

- **Практика telecli** (27 задач, сентябрь 2026): GitHub issue и PR как источник правды,
  одобрение конкретного коммита комментарием `REVIEW: APPROVED <sha>`, слияние только при
  зелёном CI и только fast-forward, сверка `main` после слияния, «не верить самоотчёту — проверять
  самому».
- **[zeroscrypt/aiac](https://github.com/zeroscrypt/aiac)** (Apache-2.0): оркестратор сам
  запускает исполнителя без окна, отдельный `git worktree` на задачу, Definition of Ready и
  Definition of Done, уроки из живых багов процесса.

Что снимает crewflow по сравнению с тем, как шла работа в telecli: исполнитель в отдельном окне
не видел сообщений, сессии множились и кончался бюджет, общая рабочая папка ломалась при
параллельной работе, каждое ревью собиралось руками.

## 3. Не цели

- Не генератор кода и не агент: crewflow ничего не пишет сам, он управляет циклом.
- Не замена CI: он читает результат CI, а не повторяет его.
- Не многопользовательский сервис: один человек, один оркестратор, локальная машина.
- Не зашивать один язык, один менеджер пакетов или одного исполнителя.

## 4. Понятия

| Понятие | Что это |
|---|---|
| Проект | Любой git-репозиторий на GitHub с файлом `crewflow.toml` в корне. |
| Задача | GitHub issue по шаблону crewflow: проблема, критерии приёмки, доказательство тестами, границы, владелец. |
| Ворота (gates) | Команды проекта, которые обязаны пройти на коммите: форматирование, линтер, тесты, сборка. |
| Прогон (run) | Один запуск исполнителя над одной задачей в своём worktree. Результат — PR с `Closes #N`. |
| Ревью | Прогон ворот на голове PR + CI + проверки оркестратора → комментарий `REVIEW: APPROVED <sha>` или `REVIEW: CHANGES REQUESTED`. |
| Слияние | fast-forward `main` до одобренного коммита, только если одобрен ровно текущий head и CI зелёный. |
| Сверка | `origin/main` == влитый коммит, issue закрыт, CI на `main` зелёный. |

## 5. Настройки: `crewflow.toml`

Один файл в корне проекта. Пример для telecli:

```toml
[project]
repo = "naghuale/tele"
default_branch = "main"
language = "ru"            # язык задач, ревью и сообщений человеку

[executor]
name = "opencode"
command = ["opencode", "run", "--dir", "{worktree}", "--format", "json", "{prompt}"]   # {model} добавляется как --model, если задана
model = ""                 # пусто — модель по умолчанию из настроек исполнителя
timeout = "90m"
fallback = ""              # запасной исполнитель, если основной недоступен

[worktrees]
root = "~/.crewflow/worktrees/{repo}"   # вне рабочей папки человека

[[gates]]
name = "format"
run = ["sh", "-c", "test -z \"$(gofmt -l .)\""]

[[gates]]
name = "vet"
run = ["go", "vet", "./..."]

[[gates]]
name = "test"
run = ["go", "test", "-race", "-count=1", "./..."]

[[gates]]
name = "lint"
run = ["golangci-lint", "run", "./..."]

[ci]
required = true            # ждать и требовать зелёный GitHub Actions на коммите
timeout = "30m"

[merge]
by = "orchestrator"        # orchestrator | executor | human
strategy = "ff-only"
```

Для проекта на другом стеке меняется только `[[gates]]`: `npm test`, `pytest`, `cargo test`,
`make check` — что угодно, что возвращает код выхода.

## 6. Команды

| Команда | Что делает |
|---|---|
| `crewflow init` | Кладёт `crewflow.toml`, шаблоны issue/PR и протокол в проект. Существующие файлы не трогает. |
| `crewflow doctor` | Проверяет, что есть `git`, `gh` (с входом), исполнитель, команды ворот; что `crewflow.toml` читается. |
| `crewflow task run <N>` | Проверяет готовность issue (DoR), создаёт ветку и worktree, запускает исполнителя с текстом issue и протоколом, ждёт завершения, проверяет, что появился PR с `Closes #N`. |
| `crewflow review <PR>` | Worktree на голове PR, прогон всех ворот, ожидание CI, сводка для оркестратора. Одобрение пишет оркестратор (`--approve` / `--request-changes <файл>`), crewflow лишь проверяет формат и что sha — текущий head. |
| `crewflow merge <PR>` | Сливает только если: есть `REVIEW: APPROVED <sha>` с sha == head, CI на head зелёный, `main` — предок head. Иначе объясняет, чего не хватает. |
| `crewflow verify <PR>` | Сверка после слияния: `origin/main`, закрытый issue, CI на `main`. |
| `crewflow status` | Что в работе: открытые задачи, прогоны, PR и их состояние. |

Все команды умеют `--json` для оркестратора и печатают человеку понятный текст на языке проекта.

## 7. Цикл задачи

```
issue (готов по DoR)
  → task run: worktree + ветка → исполнитель → PR (Closes #N)
  → review: ворота + CI + проверки оркестратора
      ├─ changes requested → task run --continue (тот же worktree и ветка) → review
      └─ approved <sha>
  → merge (ff-only, sha == head, CI зелёный)
  → verify (main, issue, CI на main)
```

Состояние прогона хранится в `~/.crewflow/state/<repo>/<N>.json` (ветка, worktree, id сессии
исполнителя, время, исход), чтобы после обрыва было видно, где остановились. Источник правды —
по-прежнему GitHub.

## 8. Инварианты безопасности

1. Исполнитель работает только в своём worktree; рабочая папка человека не меняется никогда.
2. Слияние — только fast-forward, только одобренного sha, только при зелёном CI. `--force` нет.
3. Одобрение относится к конкретному коммиту; новый коммит требует нового ревью.
4. crewflow не хранит и не печатает секреты; команды ворот получают окружение как есть.
5. Необратимые действия вне цикла (удаление веток, переписывание истории, изменение настроек
   репозитория) crewflow не делает.
6. Если исполнитель вернулся без PR, с упавшими воротами или по таймауту — это исход прогона, а
   не повод повторять молча: оркестратор решает, что дальше.

## 9. Связь с Claude Code

- `crewflow init` добавляет в `CLAUDE.md` проекта короткий раздел с ролью оркестратора и циклом.
- Skill `crewflow` для Claude Code: когда вызывать какие команды, как писать задачу по шаблону,
  как читать `--json`, когда звать человека.
- Человека зовут на: архитектурные развилки, спорные компромиссы, необратимые шаги, исчерпанные
  попытки. Всё остальное оркестратор ведёт сам.

## 10. Уроки

Два уровня:

- **Общие** — в `crewflow/protocol/LESSONS.md`: не верить самоотчёту; worktree вместо общей
  папки; детерминированные тесты вместо пауз; сверять API со схемой, а не по памяти;
  проверять «тем же путём, что программа»; одобрение привязано к sha; и уроки aiac.
- **Проектные** — в самом проекте (`docs/LESSONS.md`): для telecli это схема TDLib, отметки
  символами в режиме без цвета и т. п.

## 11. Этапы

| Этап | Результат |
|---|---|
| M1 | `crewflow.toml`, `doctor`, `task run` с headless-исполнителем и worktree. Первая задача telecli проходит через `task run`. |
| M2 | `review` с воротами и ожиданием CI, формат комментариев ревью. |
| M3 | `merge` и `verify` с проверкой инвариантов. |
| M4 | `init`, шаблоны, протокол, skill для Claude Code, `status`. |
| M5 | telecli полностью на crewflow; вторая проба на проекте другого стека. |

## 12. Открытые вопросы

- Лицензия (aiac — Apache-2.0; если заимствуем тексты уроков, нужна ссылка и NOTICE).
- Параллельные прогоны нескольких задач — после M5.
- Исполнители кроме OpenCode — интерфейс готов с M1, проверка на втором исполнителе после M5.
